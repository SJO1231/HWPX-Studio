# 검증 조건이 있는 짧은 계획

요청 범위를 실행 가능한 작업으로 만든다. 계획 작성만 요청받았다면 구현하지 않는다.
이 Skill은 작업 권한을 추가하거나 모든 단계를 사용자 승인 대기로 바꾸지 않는다.

## 입력

사용자의 목표·제약, 현재 코드·설정·기존 변경, 관련 프로젝트 계약을 확인한다.
모르는 핵심 정보는 질문으로 남긴다. 프로젝트에 없는 명령·파일·구조를 만들어 전제하지 않는다.

## 절차

1. 요청을 관측 가능한 결과로 바꾼다. 대상 사용자·입력·기대 동작 중 필요한 것을 명시한다.
2. 관련 구현·호출자·기존 테스트·최근 결정·실패 기록을 필요한 범위만 읽는다.
3. 범위와 비범위를 정하고, 기존 구조로 해결하는 가장 작은 방법을 선택한다.
4. 여러 해석이 결과를 바꾸면 차이와 질문을 제시한다. 해당 답에 의존하는 구현은 기다린다.
5. 의존 순서대로 단계를 나누고, 각 단계에 실제 확인 방법을 붙인다.
6. 기술적 성립 여부가 불확실하고 실패 비용이 큰 부분만 작은 실험으로 먼저 검증한다.
   실험은 질문·성공/실패 조건·중단 조건을 먼저 정한다. 실험 코드를 제품 코드로 자동 편입하지 않는다.
7. 변경이 누적되는 동안 계획·실제 상태가 다르면 필요한 부분만 갱신한다.
   선행 검증이 실패한 단계에 의존하는 다음 구현은 멈춘다. 독립 조사까지 일괄 중단하지 않는다.

## 출력

짧은 작업은 대화에 다음을 적는다. 기존 이슈·계획이 있으면 그곳을 갱신한다.

- 목표와 성공 조건
- 범위 / 비범위
- 확인된 사실 / 중요한 가정 / 남은 질문
- 단계별 `작업 → 확인 방법 → 통과 조건`
- 위험한 변경만: 실패 시 이번 변경을 분리·복구할 방법
- 다음 실행 한 가지

완료 조건이 정해지면 승인된 구현을 계속한다.
계획 파일·위험표·POC가 필요 없으면 만들지 않는다.

## 점검 예시

“검색 속도를 개선하라”는 요청에 먼저 데이터 규모·현재 지연·비교 환경을 확인한다.
관측 없이 새 캐시나 인덱스 서버를 계획하지 않는다.
측정 → 병목 확인 → 최소 변경 → 같은 조건의 성능·정확성 비교로 나눈다.
