# 경계·소유·계약 검토

새 체계를 만들기 전에 현재 소유자와 소비자를 확인한다.
검토 요청만 받았다면 수정하지 않는다. 구현 요청에 적용할 때도 관련 범위만 다룬다.

## 1. 소유 관계 확인

- 어떤 데이터·판정·문서 주제를 바꾸는지 명시한다.
- 기존 정본 파일·절, 구현 책임자, 입력과 소비자, 관련 테스트를 찾는다.
- 이름이 다른 같은 책임이 이미 있는지 확인한다.
- 생성 문서는 원천과 생성 경로를 찾아 고친다. 수동 사본으로 정본을 대체하지 않는다.

## 2. 변경 검토

- 새 의존이 허용된 방향을 따르는지 실제 import·호출·데이터 흐름에서 확인한다.
- 같은 의미나 권한을 다른 계층에서 다시 계산하는지 확인한다.
- 기존 값의 표시·형식 변환과 독립적인 의미 재판정을 구분한다.
- 새 layer·service·registry·cache·state·문서가 현재 문제에 필요한지 설명한다.
- 소유를 옮긴다면 실제 소비자를 찾아 함께 전환한다. 기존 파일은 소비 확인 없이 삭제하지 않는다.
- 주제 소유와 기술 사실이 모호하면 관측·가설·제안을 나누고 해당 설계 결정을 기다린다.

## 3. 필요한 계약만 검사

반복해서 깨지는 중요한 경계와 실수 비용이 큰 불변조건에 한해 기존 테스트·정적 검사 확장을 검토한다.
한 번의 작은 변경 때문에 범용 registry·문서 manifest·새 검사 프레임워크를 만들지 않는다.

검사기를 만들거나 고친다면:
- 정상 허용 사례가 통과하는지 확인한다.
- 실제 위반 사례가 실패하는지 확인한다.
- 구현이 허용하는 우회 표기·별칭·간접 경로 중 관련 있는 반례를 검사한다.
- 검사기 자체 실패와 제품 계약 위반을 구분한다.

## 결과

`변경 주제 → 현재 소유자 → 소비자 → 허용 경계 → 관측한 위반/문제 없음 → 필요한 최소 변경 → 검증`을 남긴다.
설명만 고친 것, 코드·검사를 바꾼 것, 실제 검사를 실행한 것을 구별한다.

기존 문서의 구조 검사 통과는 자연어 내용의 진실이나 외부 링크의 생존을 보장하지 않는다.
문서와 코드가 다르면 실제 관측 근거로 불일치를 보고하고, 지침을 임의로 낮추지 않는다.
