# 조각 스트레스 시험 (tools/stress)

엔진 명세 7.8절의 도구다. 서로 무관한 실제 문서 사이에서 **길고 복잡한 구간**을 통째로, 또는 쪼개서 옮기고, 서식이 그대로이고 문서가 정상인지 건마다 확인한다. 결과는 수량과 코드로만 남긴다.

## 사용법

```
node tools/stress/campaign.ts --corpus <폴더> [--seed N] [--pairs N] [--min-paras 20] [--max-paras 200]
                              [--oracle-sample N] [--no-com] [--no-rhwp] [--report <출력.json>] [--time-budget-min N]
```

| 인자 | 기본 | 뜻 |
| --- | --- | --- |
| `--corpus` | (필수) | `.hwpx`를 하위 폴더까지 모두 찾는다. 읽기만 한다 |
| `--seed` | 1 | 쌍·삽입 지점·쪼개는 위치·재실행 표본을 정하는 시드. 같은 시드와 같은 모음이면 같은 쌍과 같은 건이 나온다 |
| `--pairs` | 150 | 소스·대상 쌍의 수. 쌍마다 방식 10가지를 모두 돌린다 |
| `--min-paras`, `--max-paras` | 20, 200 | 구간 길이(최상위 문단 수). 문서가 짧으면 가능한 최대 |
| `--oracle-sample` | 30 | rhwp·한컴으로 열어 볼 건 수 |
| `--no-rhwp`, `--no-com` | 끔 | 해당 오라클을 건너뛴다(미검증으로 남는다) |
| `--report` | `tools/stress/out/report.json` | 보고 JSON. `out/`은 git에서 제외한다 |
| `--time-budget-min` | 없음 | 이 시간이 지나면 새 쌍을 시작하지 않고 거기까지로 보고한다 |

종료 코드: 0 정상, 3 모음이 실행 중 바뀐 것이 감지됨(즉시 멈추고 보고), 1 실행 오류.

그 밖의 도구:

- `node --test tools/stress/selftest.ts` — 도구 자체의 정확성 시험(합성 시험 문서의 모든 쌍에서 결함 0, 검증 항목을 일부러 틀리게 하면 잡히는지).
- `node tools/stress/repro.ts` — 첫 캠페인에서 나온 결함·거절을 합성 최소 문서로 재현한다(실제 문서를 쓰지 않는다). 엔진이 고쳐지면 "재현되지 않음"이 된다. 소스 원문의 id 중복은 검사기에 여전히 새 오류로 보이지만 계획의 `inherited`가 설명하므로 "상속 기록으로 설명되지 않는 새 오류"는 재현되지 않는다.
- `node tools/stress/narrow.ts --corpus <폴더> --report <report.json> --case p012-M4 [--code V-b:INST_DUP_ID:objectId]` — 보고서의 결함 한 건을 같은 시드·같은 쌍으로 다시 돌려 같은 결함 코드가 나는 가장 짧은 소스 구간을 찾고, 그 구간의 요소 이름·속성 이름과 검증 코드를 낸다(값은 내지 않는다).
- `python tools/com/open_check.py --out 결과.json [--pdf-dir 폴더] 파일.hwpx ...` — 한컴 COM으로 열림·쪽 수(·PDF 저장)를 JSON으로 낸다. 문서마다 작업자 프로세스를 따로 띄우고 60초가 지나면 그 작업자와 그것이 띄운 `Hwp.exe`만 종료한다. 창은 숨기고 항상 `Quit()`한다. 시작 전에 떠 있던 `Hwp.exe`는 건드리지 않고, 시간 초과가 연달아 3번이면 남은 문서를 열지 않고 중단 사유를 적는다.

## 흐름

1. **색인** — 모음의 `.hwpx`를 모두 `openPackage` + `parseDocument`로 열어 열리는 문서만 남긴다. 문서마다 최상위 문단 수, 표 수·최대 중첩 깊이, 그림·누름틀·책갈피·각주/미주·글상자·머리말/꼬리말 유무, 서로 다른 글자모양·문단모양 수, 스타일 이름 집합, 원래 검사 오류 수를 요약한다.
2. **구간 고르기** — 문서마다 구역 설정(`secPr`)이 든 문단과 짝이 모호한 누름틀이 든 문단을 피한 연속 최상위 문단 구간(길이 `min`~`max`) 중 복잡도 점수가 가장 높은 것을 고른다.
   점수 = 구간 안 객체 종류 수(`run`·`ctrl`의 자식 요소 이름) + 서로 다른 글자모양 수 + 서로 다른 문단모양 수 + 표 중첩 깊이 + 가산점(그림·누름틀 등 필드·책갈피·각주/미주·글상자가 있으면 종류마다 5점) + ln(문단 수).
   후보 길이는 `min`, 30, 50, 80, 120, 160, `max`(구간을 담을 수 있는 최대로 자른다)를 슬라이딩 윈도로 훑는다. 여러 문단에 걸친 누름틀의 안쪽에서는 구간 경계도, 쪼개는 위치도 잡지 않는다.
3. **쌍 뽑기** — 시드 고정 난수로 복잡도 상위 절반의 소스를 섞어 돌려 쓰고, 대상은 후보 12개 중 스타일 이름 집합이 다르고(+2) 글꼴 집합이 다르고(+2) 폴더가 다른(+1) 쪽을 고른다. 연쇄(M8)의 세 번째 문서는 무작위다.
4. **삽입 방식**(쌍마다 전부, 각각 한 "건")

| 방식 | 내용 |
| --- | --- |
| M1 | 통째로 대상의 마지막 문단 뒤 |
| M2 | 통째로 대상의 무작위 최상위 문단(구역 설정 없는 것) 앞 |
| M3 | 통째로 대상 첫 구역의 첫 문단 뒤 |
| M4 | 구간을 2~5개 부분으로 쪼개 같은 위치에 앞 부분 바로 뒤로 이어서 넣는다(가져오기 → 적용 → 다시 파싱 → 다음 가져오기) |
| M5 | 같은 부분들을 서로 다른 위치(구역 설정 없는 문단 앞, 또는 끝)에 넣는다 |
| M6 | 대상의 첫 표의 첫 셀 첫 문단 뒤(표가 없으면 건너뜀) |
| M7 | 같은 조각을 두 번 끝에 넣는다. 두 번째의 추가 자원은 0이어야 한다 |
| M8 | 소스 조각을 대상에 넣고, 그 결과에서 삽입된 구간을 다시 조각으로 떠서 세 번째 문서 끝에 넣는다 |
| M9 | 통째로 대상의 마지막 문단 뒤에, `planImport` 옵션 `reissueInternalDuplicates: true`로 넣는다. 조각 안에서 겹치는 id를 첫 등장만 두고 새 값으로 바꾸므로 상속한 중복이 하나도 남지 않아야 한다(계획의 `inherited.duplicateIds`가 비어 있고 검사기 새 오류에 id 중복이 없다) |
| M10 | 통째로 대상의 마지막 문단 뒤에 넣은 뒤, 삽입된 구간(표 셀·글상자 안 문단 포함)에서 시드 고정 난수로 고른 문단 3~8곳의 임의 구간에 글자 서식을, 2~4곳에 문단 서식을 적용한다(적용 → 다시 파싱 → 다음 적용). 글자 서식은 `src/format`의 편의 생성기(`charDelta`)로 만들고 드문 것(장평·자간·강조점·외곽선·위·아래첨자·밑줄·취소선 모양·음영색, 언어별 값)을 포함해 21가지, 문단 서식은 정렬 6·줄 간격 종류 4·내어쓰기·여백·앞뒤 간격 15가지다. `src/format`이 코드 있는 오류로 거절한 적용은 거절 코드별로 세고(전부 거절돼 하나도 적용하지 못한 건은 `rejected`) 다음 적용으로 넘어간다 |

5. **건마다 검증**(전부 메모리에서)

| 항목 | 내용 |
| --- | --- |
| V-a | 결과가 다시 파싱된다(`parseDocument` 예외 없음). 다시 파싱한 모델이 원본에 없던 오류를 새로 내지 않는다 |
| V-b | `compareToBaseline(대상 원본의 검사 보고서, 결과의 보고서).newErrors`가 0. 새 오류는 코드별로 센다(`INST_DUP_ID`는 문단·객체·instId·필드 id 공간까지 나누고, 중복된 값이 조각 하나 안에서 이미 두 번 이상 나오면 `.inFragment`를 붙여 소스가 가진 중복을 옮긴 것과 대상의 id와 겹쳐 생긴 것을 가른다) |
| V-c | 삽입된 문단들의 논리 텍스트가 조각의 `texts`와 같고, 소스 구간의 텍스트와 같다. 쪼갠 경우 부분들의 합이 통째와 같다. 구역 원문에서 정규식으로 뽑은 `hp:t` 글도 소스 원문과 같다 |
| V-d | 삽입된 문단의 서식 참조가 가리키는 자원의 지문이 조각의 `prints`와 같고(엔진의 지문), 별도 구현(자원을 참조까지 전개한 정규 문자열, 이진 자료는 내용 sha256)으로도 소스와 결과가 같다 |
| V-e | 삽입한 문단들을 빼면 구역 원문이 직전 문서와 같다(루트의 `xmlns:*` 추가만 허용). 대상의 기존 최상위 문단 원문이 순서대로 그대로 있고, 기존 자원 원문이 그대로이며, 바뀐 ZIP 항목은 header·구역·패키지 문서뿐이고 추가 항목은 `BinData/`뿐이다. 대상에서 없던 참조(본문·자원 안)를 가져온 자원이 채우면(기존 문단의 모양이 바뀔 수 있다) 결함이다: 새 자원의 id는 그런 참조의 id를 건너뛴다(`FILLS_DANGLING`). 기준선에서 한컴이 받아 주는 경고(`RES_DANGLING_TOLERATED`: 탭 목록이 비었는데 tabPrIDRef=0)였던 같은 참조가 목록이 차서 검사기 오류로 올라온 것은 원래 있던 문제로 센다(V-b, 저장 게이트와 같은 판정 `splitTolerated`) |
| V-f | 문단·표·그림·누름틀·책갈피 증감과 자원·이진 자료 증감이 계획 `summary`의 예고와 같다. 검사기 census의 증감도 같다. header 목록의 개수 속성(`itemCnt`·`fontCnt`)이 원본에서 맞던 목록에서 어긋나지 않고(가져오기가 새로 만든 목록은 계획 `summary.createdLists`만큼 슬롯이 늘고 그 개수 속성도 실제 항목 수와 맞아야 한다), 같은 이름의 스타일 중복이 원본보다 늘지 않는다. M7의 두 번째 가져오기는 추가 자원·이진 자료 0 |
| V-g | 결과의 모든 `binaryItemIDRef`가 manifest와 ZIP 항목에 있다(대상에 이미 없던 참조·빈 값은 뺀다). 새 manifest 항목은 ZIP 항목이 있고 새 ZIP 항목은 manifest에 등록돼 있다 |
| V-h | 표본(약 20%)을 입력을 새로 읽어 다시 실행해 단계마다 출력 바이트(sha256)가 같다 |
| V-i | 객체 id·instId·누름틀 시작 id의 중복이 대상 원본보다 늘지 않는다(자리값 `0`·빈 값 제외). V-b와 같이 `.inFragment`로 가른다. 계획의 `inherited.duplicateIds`가 기록한 값은 뺀다 |
| V-m | (M10만, 적용마다) 모든 문단의 논리 텍스트가 변하지 않는다. 적용한 구간 밖 글자와 다른 문단의 서식 지문(독립 구현 `canon.ts`의 참조 전개)이 변하지 않는다(글자 서식이면 문단모양·스타일도, 문단 서식이면 글자모양도). 적용한 구간의 run(문단 서식이면 그 문단)이 가리키는 자원 요소에 요청한 속성이 있다(자원 요소에서 직접 읽는다). 서식 변경을 마친 문서는 V-a·V-b·V-e·V-f·V-g·V-i도 거친다(V-e는 줄 배치 캐시를 뺀 원문으로 비교하고, 서식 변경이 파생한 자원도 대상의 없던 참조를 채우면 결함이다) |

6. **분류** — 건마다 하나다.
   - `ok`: 모든 검증 통과.
   - `rejected:<코드>`: 엔진이 코드 있는 오류(`HwpxError`)로 거절했고 출력이 없다(`plan`·`apply`·`extract` 단계). `EDIT_STALE`, `EDIT_OVERLAP`, `EDIT_RANGE`, `FRAG_SCHEMA`, `FRAG_SELECTION`, `FRAG_INSERT_POINT`는 정책이 아니라 내부 일관성 오류이므로 보고서에서 따로 읽는다.
   - `defect:<V항목>:<코드>`: 출력이 났는데 검증이 실패했거나, 코드 없는 예외(`defect:exception:<오류 이름(단계)>`, 엔진 소스 안의 위치를 `site`로 남긴다). 다시 파싱 실패는 `defect:V-a:<코드>`. 상속으로 설명되지 않는 새 오류도 여기 센다(`.inFragment`가 붙은 id 중복은 소스 조각 안의 중복인데 계획이 기록하지 않았다는 뜻이다).
   - `inherited:<V항목>:<코드>`: 계획의 `inherited`(조각이 소스에서부터 갖고 있던 문제)로 설명되는 새 오류. 검사기 오류는 엔진의 저장 게이트와 같은 판정(`explainInherited`: 코드와 메시지에 든 id 값을 `inherited`와 맞춘다)으로, 모델 오류와 이진 자료 정합은 `inherited.danglingRefs`의 (종류, id)로 가른다. 조각 안에서 겹치는 id(`duplicateIds`: 문단 id·객체 id·instId·누름틀 시작 id), 소스에서 없던 참조(`danglingRefs`)가 해당한다. 같은 이유로 M7의 두 번째 가져오기가 자원을 또 추가하는 경우도 여기에 센다(대상에 같은 id가 있으면 첫 가져오기의 자원이 대상의 자원을 가리키게 되어 지문이 달라진다). 설명되지 않는 새 오류는 결함이다. 결함 수에는 넣지 않고 따로 센다. 빈 `binaryItemIDRef`는 참조 없음이라 기록도 오류도 없다.
   - `skipped:<코드>`: 방식을 적용할 수 없다(대상에 표가 없음, 쪼갤 곳이 없음). 도구 안의 예외는 `skipped:TOOL_ERROR:*`로 센다.
7. **오라클 표본**(`--oracle-sample`) — 결함이 아닌(`ok`) 건 중 위험이 큰 것(그림·누름틀·중첩 표·글상자·각주·책갈피·머리말/꼬리말 포함, 긴 구간, 쪼개기·연쇄·표 셀)을 위험 점수로 골라(한 방식이 40%를 넘지 않게) OS 임시 폴더 `hwpx-studio-stress/`에 저장한다. 표본의 20%는 서식 변경 조합(M10), 20%는 셀 안 삽입(M6, 그중 절반까지는 계획이 `FRAG_CELL_MAY_CLIP` 경고를 낸 건), 10%는 없던 목록을 만들어 새로 통과하게 된 건(계획 `summary.createdLists > 0`)에 먼저 배정하고 나머지를 위험 순으로 채운다. 이 건들은 보고에서 따로 센다(`cellMayClip`, `listCreated`, `formatCombination`: 쪽 수 변화 분포). 표본을 열어 본다:
   - rhwp: `hwpx-edit/.cargo-root/bin/rhwp.exe info <파일> --json`의 종료 코드와 쪽 수(출력에서 쪽 수·문단 수·경고 수만 꺼낸다),
   - 한컴: `tools/com/open_check.py`로 열림·쪽 수·PDF 저장,
   - 대상 원본 사본도 같이 열어 쪽 수 변화(결과 − 원본)의 분포를 낸다. 쪽 수가 줄면 이상 신호로 센다(내용을 넣기만 했으므로).
   실행이 끝나면 임시 폴더를 지운다.

## 보고 JSON

값·이름이 없다. 수량·코드·식별자만 있다.

- `corpus`: `.hwpx` 수·총 크기·수정 시각 최댓값과 (상대 경로, 크기, 수정 시각)의 sha256을 시작과 끝에 재서 `unchanged`를 낸다.
- `index`: 문서 특성의 분포(최솟값·중앙값·90분위·최댓값)와 보유율(그림·누름틀·중첩 표·각주·글상자·머리말/꼬리말 등), 원래 검사 오류 코드별 문서 수.
- `pairs`, `windows`: 쌍의 수와 쓰인 구간의 길이·복잡도 분포.
- `methods`, `totals`, `codes`: 방식별 건수와 ok/rejected/inherited/defect/skipped 수, 코드별 집계(거절·결함 대표/전체·상속·건너뜀·거절 세부·검사기 새 오류 이슈 수·계획 경고).
- `formatCombination`(M10): 건 수, 서식을 하나라도 적용한 건 수, 적용한 서식 종류별 건수(`char:<종류>`·`para:<종류>`, 앞의 `rare:`는 드문 서식), 이미 같은 모양이라 바뀌지 않은 적용 수, `src/format`의 거절 코드별 수와 종류·코드별 수. `inheritedPlan`: 계획이 상속을 기록한 건 수(방식별). `createdLists`: 없던 목록을 만든 건. `cellMayClip`: M6 중 계획이 셀 안 삽입 경고를 낸 건과 아닌 건.
- `defects`: 결함 건의 식별자(`p<쌍 번호>-M<방식>`)·코드·소스/대상 식별자·구간 서수. `narrow.ts`가 이것을 읽는다.
- `resources`: M1의 자원 재사용/추가 분포, 이진 자료 재사용/추가, 스타일 이름 충돌 수, 재발급 id 수, M7 두 번째의 추가 자원, 소스에서 이미 없던 대상의 종류. `fragmentListNeeds`는 쌍마다 통째 조각이 요구하는 자원 종류와 대상 header의 목록 유무(`FRAG_NO_LIST` 거절 사유 대조).
- `toolCoverage`: 검증이 실제로 비교한 양(비교한 문단 수, 참조 수, 건너뛴 참조 수 등). 검증이 아무것도 비교하지 않았는데 통과하는 일을 가려내려는 것이다.
- `determinism`, `time`, `oracle`(rhwp·한컴 결과, 표본 구성, 건별 쪽 수·문단 수, rhwp가 센 문단 수 증가와 계획 예고의 대조), `tempDirEmptiedAtEnd`, `engine`(엔진 소스 지문, 다른 담당이 엔진을 고치는 중일 때 결과와 대조하려는 것).

## 개인정보 규칙

- 모음 폴더는 읽기만 한다(쓰기·이동·삭제 호출이 없다). 시작과 끝에 목록 요약을 재서 바뀌지 않았음을 확인하고, 실행 중에도 쌍의 파일 크기·수정 시각과 50쌍마다 전체 목록을 다시 확인한다. 바뀐 것이 감지되면 멈춘다.
- 모음 경로는 코드·문서·보고서·로그 어디에도 적지 않는다. 인자로만 받는다.
- 파일 이름과 문서 내용은 보고서·로그·화면에 남기지 않는다. 사례 식별자는 모음 폴더 기준 상대 경로의 sha256 앞 10자다. 오류는 코드와 엔진 소스 안의 위치만 남기고 메시지는 남기지 않는다. `narrow.ts`도 요소 이름·속성 이름만 낸다.
- 결과물은 OS 임시 폴더 아래 `hwpx-studio-stress/`에만 쓰고 끝나면 폴더째 지운다.

## 한계와 다음에 넣을 것

- 서식 변경 조합(M10)은 통째로 넣은 한 방식에만 붙였다(쪼개기·연쇄·셀 안에는 붙이지 않았다). 서식 변경은 그 구역의 줄 배치 캐시를 전부 지우므로(명세 7.7) M10의 V-e는 대상의 기존 문단 원문을 줄 배치 캐시를 뺀 원문으로 견준다.
- 구간 선택이 여러 문단에 걸친 누름틀을 가르는 경우(조각 안에서 시작과 끝이 갈리는 경우)는 시험하지 않는다. 그런 선택은 소스 쪽에서 피한다.
- 구역 설정(`secPr`)이 든 문단은 구간에서 뺀다(엔진 1차 범위 밖). 개요 번호처럼 구역 설정이 가리키는 서식은 대상의 것을 따른다.
- 쪽 수 비교는 대상 원본 대비 증가 여부만 본다. 쪽 모양·줄바꿈의 눈으로 보는 비교는 하지 않는다.
- 한컴 COM은 작업자를 문서마다 띄우므로 표본이 많으면 오래 걸린다(문서당 3~10초).


## 표 조정 스트레스 시험 (`tables.ts`, 엔진 명세 7.9절 B7)

```
node tools/stress/tables.ts --corpus <폴더> [--seed N] [--docs M] [--ops K] [--com-sample N] [--no-com] [--prefer-merged-only] [--report <출력.json>]
```

`--prefer-merged-only`: 병합 셀로만 덮인 열(colSpan 1인 셀이 하나도 없는 열)이 있는 표가 든 문서를 먼저 고르고, 문서 안에서도 그런 표를 우선한다(열 경계를 균등 분배로 추정하는 표를 많이 시험하려는 용도).

실제 문서 모음에서 열리는 문서 가운데 표가 든 것을 시드 고정 난수로 `--docs`개 고르고, 문서마다 병합·중첩이 든 표를 우선해 최대 6개를 골라 표마다 연산 3가지를 무작위로 적용한다(문서마다 원본에서 따로 시작한다. 연쇄하지 않는다). 연산은 14가지: 표 설정(`props`), 셀 설정(`cellProps`, 테두리 파생 포함), 열 너비(`columns`), 비례 조정(`scale`), 행 높이(`rowHeights`), 행 삽입(`insertRows`), 행 반복(`repeatRows`), 열 삽입·삭제(`insertColumns`·`deleteColumns`), 병합(`merge`), 분할(`split`), 표 복제(`clone`), 저장 게이트를 거치는 템플릿 액션(`gateProps`: 설정+크기, `gateRepeat`: 행 반복 0~4개). 인자는 표의 격자에서 무작위로 뽑으므로 거절되는 건도 많다.

건마다 확인한다(전부 메모리에서). 다시 파싱됨, 검사기 `compareToBaseline` 새 오류 0(`splitTolerated`), 보존 계약(`verifyPreservation`: 편집 구간 밖 원문 동일), 표 불변식(`checkTableGeometry`: 속성만 바꾸는 연산은 표마다 원본보다 나빠지지 않음, 구조 연산은 원본에 없던 종류의 위반이 없음), 연산별 사후 조건(요청한 속성·너비·행 수·열 수·병합 수·수량 증감을 다시 읽어 견줌), 표본(약 1/8)의 결정성(같은 입력 → 같은 바이트).
엔진의 열 너비 추정을 쓰지 않는 독립 검사도 한다(표 수가 달라지는 건 — 표 복제, 마지막 행을 지워 표가 사라지는 행 반복 — 은 뒤 표의 서수가 밀려 뺀다): 출력의 `tr`·`tc`에서 주소·병합·너비를 직접 읽어 행마다 그 행을 덮는 셀 너비(위에서 내려온 세로 병합 포함)를 더하고, 원본에서 (a) 행 합이 표 너비와 같았다면 결과에서도 같고, (b) 행끼리 합이 같았다면 결과에서도 같고, (c) 모든 셀 너비가 1 이상이었다면 결과에서도 1 이상이다(`widths:*` 결함 코드).
행·열·표를 복제하면 원본이 이미 갖던 오류(없는 서식을 가리키는 참조 등)도 복제되어 개수가 는다. 같은 오류(코드·메시지)가 원본에 있었으면 `inherited`(상속)로 세고 결함에서 뺀다.

분류: `ok`, `inherited`, `rejected:<코드>`(엔진이 `HwpxError`로 거절, 출력 없음. `EDIT_*`·`TABLE_INTERNAL`은 내부 일관성 오류라 결함), `defect:<항목>`, `skipped`(적용할 수 없는 인자). 저장 게이트를 거친 건이 `GATE_*`·`PRESERVE_*`·`REREAD_*`로 실패하면 결함이고 그 밖의 코드는 거절이다.

한컴 표본(`--com-sample`, 기본 20): `ok`인 건 중 위험(병합·중첩·구조 연산)이 큰 것을 문서마다 하나씩 골라 OS 임시 폴더에 저장하고 `tools/com/open_check.py`로 연다(원본도 같이 열어 쪽 수 변화를 본다). 끝나면 폴더를 지운다. `--no-com`이면 건너뛴다.

보고 JSON(`tools/stress/out/tables-report.json` 기본, git에서 제외): `corpus`(수량·변경 없음 확인), `observed`(표 크기 기준·격자 규칙성·표 높이/너비와 행/열 합의 관계·셀 영역 목록 등의 분포), `selection`, `totals`, `byKind`, `codes`, `gateCodes`, `defectCodes`와 `defects`(식별자 `<문서 id>-t<표 번호>-<연산>`·코드·인자 요약), `determinism`, `time`, `com`. 값·이름이 없고 식별자는 상대 경로 sha256 앞 10자다. 개인정보 규칙은 위 조각 스트레스 시험과 같다(모음은 읽기만 하고 경로는 인자로만 받는다).
