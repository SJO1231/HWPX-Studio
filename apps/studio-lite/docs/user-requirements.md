# HWPX·TXT 조건분기형 템플릿 도구 — 사용자 요구

기준일: 2026-10-05. 사용자 요구 R1~R10과 승인한 검토 아홉 가지를 통합했다. 화면 지적 32건은 작업 묶음 네 개로 추적한다.

이 문서는 **만들어야 할 동작과 미정인 설계**를 구분한다. 문서 작성·이슈 등록은 구현 또는 실제 자료 검증 완료를 뜻하지 않는다. 이전 [독립 설계자용 기술 검토 의뢰서](architect-review-brief.md)는 당시의 근거 기록으로 보존하며, 최신 사용자 요구는 이 문서를 따른다. 공용 API·저장·선택 계약은 [엔진 명세](../../../docs/engine-spec.md), 화면 계약은 [스튜디오 명세](../../../docs/studio-spec.md)를 참조한다. 요구와 공용 계약이 충돌하면 담당자가 계약 변경을 검토하고 앱에서 우회 규칙을 만들지 않는다.

## 1. 읽는 방법과 목적

| 표시 | 의미 |
| --- | --- |
| 요구 | 만들어야 하는 사용자 동작·검사 기준 |
| 현재 생각 | 사용자 선호. 비교 결과에 따라 조정 가능 |
| 검토 | 구현 후보. 채택·구현 완료로 간주하지 않음 |
| 미정 | 설계자가 대안을 비교해 제안할 항목 |

**목적 [요구]**: 기존 문서를 한 번 템플릿으로 만들어 두고 다음부터 업무 데이터와 경우 선택만 바꿔 반복 생성한다. 주 대상은 공고서, 다음은 제재 심의안·내부 기안문이다. 주 형식은 **HWPX와 TXT**, Markdown은 보조다. 기존 두 엔진과 공통 템플릿 개념을 유지하되 특정 화면 배치나 Markdown 중심 입력을 목표로 고정하지 않는다.

**제작 흐름 [요구]**: 문서 선택(1개 또는 여러 개) → 추천 검토 → 영역 지정·이름·데이터 연결 → 블록·분기·순서 구성 → 템플릿 저장.

**사용 흐름 [요구]**: 템플릿 선택 → 업무 건 선택 → 분기점마다 블록 선택 → 바로 생성 또는 미리 보기 후 생성 → 다른 업무 건에 재사용.

매 생성마다 분석·연결을 반복하지 않는다. 템플릿 수정과 이번 건의 선택은 별도 작업이며 이번 건의 변경이 템플릿에 조용히 반영되지 않는다.

## 2. 개념과 화면 용어

개념 구분은 [요구]다. 화면 이름은 [현재 생각]을 기본으로 하되, **필드의 화면 용어는 이번 확정에 따라 ‘입력 항목’**이다.

| 내부 개념 | 뜻 | 화면에서 보일 것 |
| --- | --- | --- |
| 템플릿 | 재사용할 문서 구조 + 연결·분기 설정 | 템플릿 이름, 용도 |
| 필드 | 값이 들어가는 자리라는 개념 | 입력 항목: 업무 이름, 연결된 데이터 항목, 현재 값 |
| 앵커 | 바꾸거나 넣을 문서 위치 | 어느 제목·문단·표인지와 원문 강조 |
| 앵커+ | 경우에 따라 블록을 고르는 논리적 분기점 | 어떤 경우에 어떤 내용을 쓰는지 |
| 블록 | 그 자리에 들어갈 내용 한 가지. 글+필드, HWPX는 서식·표 포함 | 구분되는 제목, 실제 문구, 다른 선택지 |
| 업무 건 | 적용할 데이터 한 건 | 공사·물품·용역 이름과 값 |

**필드** = 값이 들어가는 자리(개념). **누름틀**은 HWPX에서 필드를 표현하는 방식 중 하나이고, `{{키}}`는 HWPX·TXT 공통의 다른 표현이다. 화면 용어는 **입력 항목**이다.

앵커+는 드래그한 물리 범위와 같지 않다. 범위 지정(어디)과 분기 구성(어떤 경우에 무엇)은 별도 조작·별도 저장이다. 사용자가 내부 용어를 배워야 하는 화면을 피하고 ‘어느 부분·무슨 값·어떤 경우’로 보인다. [요구]

## 3. 요구사항

### R1 단일 문서 제작 [요구]

문서 하나로 바로 시작한다. 발견한 누름틀·`{{키}}`·라벨 옆 빈칸·제목·표를 후보로 보이고, 사용자가 확정하거나 직접 영역을 지정한다. 비교 문서 없이도 템플릿 저장과 반복 생성까지 끝낼 수 있어야 한다.

### R2 복수 문서 제작 [요구]

여러 문서의 공통·차이에서 값 후보·공통 문구·블록 후보·위치·분기점을 추천하고, **어느 문서의 어떤 차이 때문인지** 보인다.

비교할 문서 묶음과 **출력 기준 문서는 사용자가 지정**한다. 첫 파일을 묻지 않고 기준으로 삼지 않는다. 사용자가 묶지 않은 문서는 한 템플릿으로 합치지 않는다. 사용자가 제공한 공고서 두 사례는 독립 사례로 유지한다.

공통·차이에서 찾는 것은 분기 **후보**까지이고, 그 차이가 어떤 업무 조건 때문인지는 사용자가 확인·입력한다.

- [현재 생각] 복수 문서 제작은 TXT부터 먼저 구현한다.
- [검토] Kordoc의 후보 탐지 원리를 참고해 예상 누름틀·앵커와 앵커+ 후보를 찾는다. 활용 범위는 확인하며 코드·의존성 도입과 원리 참고를 구분한다.

### R3 추천 표시와 확정 [요구]

추천은 초안이며 확정과 구분한다. 항목마다 문서, 원문 부위, 추천 이름과 현재 값, 종류(값/블록/분기), 근거를 보인다.

위치 표시는 형식별이다. **HWPX는 쪽·제목·원문 부위, TXT는 줄 범위·제목. 없는 정보를 만들어 붙이지 않는다.**

쪽·제목별로 묶고 ‘유지할 것 고르고 나머지 한 번에 제외’, 되돌리기, 원문 이동, 수동 추가, 이름·연결 수정, 확정을 제공한다. TXT에서는 줄 범위·제목을 사용한다. **추천 제외는 원문 삭제가 아니다.**

### R4 영역 지정과 이름 [요구]

주석 달듯 드래그·선택 → 항목 추가 → 이름 정하기 → 데이터 연결 → 결과 확인으로 이어진다. 이름을 정하는 경로는 다음 세 가지다.

1. 문서 라벨·제목·문맥에서 추천.
2. JSON·DB·XLSX 컬럼 중 선택.
3. 직접 입력.

누름틀 이름은 가급적 데이터 원천 이름과 일치시킨다. 이름이 원천 키와 같으면 연결 **후보를 자동으로 맞춘다**. 승인은 별도 동작이다(R10). **표시 이름·원천 키·문서 위치는 각각 저장**하며, 표시 이름을 바꿔도 원천 키는 바꾸지 않는다.

의미 기반 추천의 정확도는 별도 검증 대상이다. [검토] 향후 Jev 활용은 [미정]이다.

### R5 데이터 연결과 업무 건 [요구]

원천·컬럼·선택 건의 실제 값·연결 여부·문서 위치를 한 화면에서 본다. 업무 건을 바꾸면 값과 문서 결과가 함께 바뀐다.

업무 건을 바꾸는 동안 **‘갱신 중’**을 표시하고, **현재 건과 일치하는 결과만 내려받을 수 있다. 이전 건의 결과가 섞여 보이지 않는다.**

DB 종류·직접 접속·XLSX 복잡 서식 범위는 [미정]이다. 미정인 데이터 접속 범위를 임의로 넓히지 않는다.

### R6 블록과 분기 [요구]

블록은 재사용·선택에 맞는 크기로 만들며 번호 제목 전체를 강제하지 않는다. 기본 이름은 내용 제목 또는 서로 구분되는 번호 이름으로 만들고 사용자가 바꿀 수 있다.

분기 화면에서 **위치 × 경우 → 선택 블록 → 순서**가 한눈에 보이고, 현재 선택·미선택·결과 위치가 드러난다. 조건 자동 선택과 수동 선택을 구분해 표시하고, 확정한 수동 선택을 자동으로 바꾸지 않는다.

분기점 하나당 블록 **하나**다(현재 엔진 계약 8.8.6). **재확인 필요·동률은 생성 차단**이다. 두 분기점에 각각 작은 블록을 고르는 것으로 대부분을 해결한다. **한 자리에 여러 블록 + 순서**는 [미정]으로 두고 계약 담당이 비교한다. 하위 분기·블록 안 블록도 [미정]이다. 화면 시안에서 미정인 다중 선택 계약을 먼저 구현하지 않는다.

### R7 편집과 미리 보기 [요구]

선택 항목에 집중해 편집하고 원래 위치·스크롤로 돌아온다. 닫을 때 작성 중 내용을 조용히 버리지 않는다. 블록으로 만든 뒤에도 편집 가능 범위를 확인해 반영한다. Ctrl+Z가 글·필드 삽입·블록·조건 변경에 일관되게 동작한다.

**선택 승계**: 같은 업무 건 안에서 데이터가 바뀌어도 확정한 수동 선택은 유지한다. **다른 업무 건으로 옮길 때는 묵시적으로 승계하지 않고**, **‘이전 건의 선택 복사’**를 명시 동작으로만 둔다. 복사된 선택의 유효성은 기존 템플릿·블록 내용 및 재확인 계약을 따른다.

**편집 동작**: 집중 편집은 **닫기 / 취소 / 초안 보관 / 템플릿(공용 블록)에 반영 / 이번 건에만 반영**을 구분한다. **이번 건 수정이 공용 블록·템플릿을 바꾸지 않는다.** 템플릿과 공용 블록 원형은 같은 저장 범위가 아니며, 반영 대상을 구분하고 각 대상의 기존 저장·전파 계약을 따른다.

| 형식 | 요구되는 편집·확인 흐름 |
| --- | --- |
| TXT | 본문·블록 직접 수정과 결과 생성 |
| HWPX | 원문 위치를 보며 지정·지원되는 편집·결과 확인 |
| MD | 보조 형식 |

HWPX의 **값 변경 / 문단 편집 / 블록 교체 / 표·서식 자유 편집**은 지원 여부를 나눠 표시한다. 이를 모두 지원한다고 표시하지 않는다. 원본은 보존하고 결과는 별도로 만든다.

### R8 반복 생성 [요구]

템플릿 선택 → 업무 건 → 블록 선택 → 보완 → 바로 생성 또는 미리 보기 후 생성으로 이어진다. **미리 보기는 값·블록·순서가 반영된 결과**다. 저장한 템플릿을 다른 업무 건에도 재사용하며 매번 분석·연결을 반복하지 않는다.

일괄 생성 규모·조작은 [미정]이다.

### R9 화면 [요구]

쉽고 간단하며 동선을 최소화하고 안내는 필요한 순간에 제공한다. 초기 선택(문서·데이터 원천)은 접고 요약만 남긴다. 문서가 중심 공간이며 분기·참조 목록은 일정 이상 보인다. 접힌 곳에 무엇이 있는지 알 수 있어야 한다.

상단은 작은 메뉴·도구줄(열기·최근·저장·생성), 확대율·줄 위치는 하단 상태줄에 배치하고 내부 주소(구역·오프셋)는 보이지 않는다. **1366×768·1024×768**에서 동작해야 한다.

[현재 생각] VS Code·Cursor·Codex·Obsidian의 접기·집중 편집·선택 상세·위치 유지 방식을 참고한다. 특정 제품의 외형을 그대로 복제하는 요구는 아니다.

### R10 안전 [요구]

승인 안 된 후보 미주입, 이중 치환 금지, 중복 매핑 거부, 오래된 결과 내려받기 차단을 유지한다. 지원 안 되는 작업은 이유를 보인다. 이름 일치·추천·후보 승격을 승인과 혼동하지 않는다. 사용자의 원본 문서와 원본 데이터는 덮어쓰지 않는다.

## 4. 검토 후보와 미정 사항

### 4.1 편집 배치 [검토]

| 대안 | 비교할 내용 |
| --- | --- |
| 문서 중심 작업창 + 선택 시 옆 상세 | HWPX의 기본 후보. 원문 위치를 보며 선택하고 뷰어는 접을 수 있음 |
| 블록 집중 편집(확대창) | 블록 수정 때 열고 닫으면 원래 선택·스크롤로 복귀. TXT·HWPX 공통 |
| 블록 삽입 때만 뷰어 | TXT 후보. 평소 한 창 편집. 본문 편집창에서 위치 선택이 가능하면 별도 뷰어 필요성도 비교 |
| 단계별 화면(추천→편집→생성) | 처음 쓰는 사람에게 유리할 수 있음. 제작 흐름에만 적용하는 후보 |
| 원문·결과 병행 | 미리 보기 단계에서 전환 또는 병행하는 후보 |
| 중앙 vs 오른쪽 편집 | 고정하지 않음. 같은 독립 사례와 같은 작업으로 왕복 횟수·보이는 양·위치 복원을 비교 |

검토 권고는 **HWPX: 문서 중심 + 옆 상세 + 블록 확대 편집**, **TXT: 한 창 편집 + 삽입 때만 필요한 위치 안내/뷰어**다. 이 권고는 배치 확정이 아니다.

분기는 **경우를 열, 분기점을 행으로 한 표**에 선택 블록과 순서를 적는 형태를 먼저 시안으로 본다. 업무 조건의 모든 조합을 무조건 펼치는 방식을 확정하지 않는다. 필요한 경우를 등록한 표와 조건으로 좁혀 보는 표를 비교할 수 있다. [검토]

### 4.2 편집 기술 [미정·검토]

HTML 편집기 + HWPX 처리 / rhwp 편집 모드 / txt→txt는 비교 대상이다. 확인할 것은 선택 위치↔생성 대상 연결 안정성, 블록 재편집·재적용, 글 수정과 구조·서식 편집의 지원 범위, 미리 보기와 저장 파일 일치, 미지원 안내다.

**rhwp는 현재 계약대로 읽기 전용**이다. 편집 모드는 **왕복 보존 비율 측정 뒤 후보로만** 다룬다. 검토 후보라는 이유로 편집·직렬화 API를 사용하지 않는다. **Kordoc은 원리 참고와 의존성 도입을 구분**한다. 새 편집기나 의존성 도입을 이 요구 문서에서 승인하지 않는다.

### 4.3 계약 결정 대기

- TXT·MD 조건 입력 문법과 엔진 9절의 연결은 [#58](https://github.com/SJO1231/HWPX-Studio/issues/58)에서 결정한다. **계약 결정 전에는 보류한 text-template.ts 및 연결 변경 stash를 꺼내지 않는다.**
- 한 자리에 여러 블록+순서, 하위 분기, 블록 안 블록은 계약 담당자가 비교한다.
- DB 종류·직접 접속·복잡 XLSX, 일괄 생성 규모·조작, Jev 도입과 의미 추천 정확도 목표는 미정이다.

## 5. 확인 기준과 근거 구분

다음 인수 확인은 **실제 자료로** 한다. 사용자 자료는 읽기 전용이며 두 독립 공고서 사례를 임의로 묶지 않는다. 복수 제작 확인에는 사용자가 별도로 지정한 비교 문서 묶음과 기준 문서가 필요하다. 자료가 부족하면 미검증으로 남긴다.

합성 회귀와 필수 `npm run verify`는 별도로 유지한다. 구현 PR은 검사 명령·수치·미검증 범위를 적는다. 실제 자료의 파일 이름·본문·값·개인 경로·토큰을 코드·문서·이슈·PR에 싣지 않는다. 근거는 비식별 해시·수량·판정으로 기록한다.
