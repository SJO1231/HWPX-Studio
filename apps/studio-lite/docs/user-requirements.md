# HWPX·TXT 조건분기형 템플릿 도구 — 사용자 요구

기준일: 2026-10-05. 사용자 요구 R1~R10과 승인한 검토 아홉 가지를 통합했다. 화면 지적 32건은 작업 묶음 네 개로 추적한다. 2026-10-05 결정 기록(용어·주 흐름·블록·화면·후순위·정리)은 8절이다.

이 문서는 **만들어야 할 동작과 미정인 설계**를 구분한다. 문서 작성·이슈 등록은 구현 또는 실제 자료 검증 완료를 뜻하지 않는다. 이전 [독립 설계자용 기술 검토 의뢰서](architect-review-brief.md)는 당시의 근거 기록으로 보존하며, 최신 사용자 요구는 이 문서를 따른다. 공용 API·저장·선택 계약은 [엔진 명세](../../../docs/engine-spec.md), 화면 계약은 [스튜디오 명세](../../../docs/studio-spec.md)를 참조한다. 요구와 공용 계약이 충돌하면 담당자가 계약 변경을 검토하고 앱에서 우회 규칙을 만들지 않는다.

## 1. 읽는 방법과 목적

| 표시 | 의미 |
| --- | --- |
| 요구 | 만들어야 하는 사용자 동작·검사 기준 |
| 현재 생각 | 사용자 선호. 비교 결과에 따라 조정 가능 |
| 검토 | 구현 후보. 채택·구현 완료로 간주하지 않음 |
| 미정 | 설계자가 대안을 비교해 제안할 항목 |

**목적 [요구]**: 기존 문서를 한 번 템플릿으로 만들어 두고 다음부터 업무 데이터와 경우 선택만 바꿔 반복 생성한다. 주 대상은 공고서, 다음은 제재 심의안·내부 기안문이다. 주 형식은 **HWPX와 TXT**, Markdown은 보조다. 기존 두 엔진과 공통 템플릿 개념을 유지하되 특정 화면 배치나 Markdown 중심 입력을 목표로 고정하지 않는다.

**제작 흐름 [요구]**: 문서 선택(1개 또는 여러 개) → 추천 검토 → 영역 지정·이름·데이터 연결 → 블록·분기·순서 구성 → 템플릿 저장.

**결정(2026-10-05)**: 주 흐름은 블록 중심이다(8.2). 문서에서 범위를 정해 블록으로 저장하는 "복사해서 가져오기"(블록 만들기)도 제작 모드의 일이다. 블록은 템플릿이 아니다(8.1). 첫 구현 조각은 구간 떼기 → 블록 저장 → 저장소 → 바탕 문서의 분기점에 갈아끼워 생성이고, 입력 항목 연결·경우는 그다음이다(8.7).

**사용 흐름 [요구]**: 템플릿 선택 → 업무 건 선택 → 분기점마다 블록 선택 → 바로 생성 또는 미리 보기 후 생성 → 다른 업무 건에 재사용.

매 생성마다 분석·연결을 반복하지 않는다. 템플릿 수정과 이번 건의 선택은 별도 작업이며 이번 건의 변경이 템플릿에 조용히 반영되지 않는다.

## 2. 개념과 화면 용어

개념 구분은 [요구]다. 화면 이름은 [현재 생각]을 기본으로 하되, **필드의 화면 용어는 이번 확정에 따라 ‘입력 항목’**이다.

| 내부 개념 | 뜻 | 화면에서 보일 것 |
| --- | --- | --- |
| 바탕 문서 | 템플릿의 바탕이 되는 원본 문서의 사본(예전 "뼈대") | 문서 이름, 종류, 열었을 때 원문 |
| 템플릿 | 바탕 문서 + 입력 항목 연결 + 분기 구성(블록은 템플릿이 아니다) | 템플릿 이름, 용도 |
| 필드 | 값이 들어가는 자리라는 개념 | 입력 항목: 업무 이름, 연결된 데이터 항목, 현재 값 |
| 앵커 | 바꾸거나 넣을 문서 위치 | 어느 제목·문단·표인지와 원문 강조 |
| 앵커+ | 경우에 따라 블록 하나를 고르는 논리적 자리 | 분기점: 어떤 경우에 어떤 블록을 쓰는지 |
| 블록 | 그 자리에 들어갈 내용 한 가지. 글+필드, HWPX는 서식·표 포함 | 구분되는 제목, 실제 문구, 다른 선택지 |
| 경우 | 이름을 붙인 조건 조합. 업무 건은 조건으로 경우에 배정된다 | 경우 이름(예: 중소기업 일괄구매) |
| 업무 건 | 적용할 데이터 한 건 | 공사·물품·용역 이름과 값 |
| 제작 모드 · 사용 모드 | 템플릿을 만드는 화면 / 저장된 템플릿으로 생성하는 화면. 메뉴는 하나, 시작점이 다름 | 상단의 한 단어 |

**필드** = 값이 들어가는 자리(개념). **누름틀**은 HWPX에서 필드를 표현하는 방식 중 하나이고, `{{키}}`는 HWPX·TXT 공통의 다른 표현이다. 화면 용어는 **입력 항목**이다.

용어의 정의와 이유는 8.1에 있다. 앵커+는 드래그한 물리 범위와 같지 않다. 범위 지정(어디)과 분기 구성(어떤 경우에 무엇)은 별도 조작·별도 저장이다. 사용자가 내부 용어를 배워야 하는 화면을 피하고 ‘어느 부분·무슨 값·어떤 경우’로 보인다. [요구]

## 3. 요구사항

### R1 단일 문서 제작 [요구]

문서 하나로 바로 시작한다. 발견한 누름틀·`{{키}}`·라벨 옆 빈칸·제목·표를 후보로 보이고, 사용자가 확정하거나 직접 영역을 지정한다. 비교 문서 없이도 템플릿 저장과 반복 생성까지 끝낼 수 있어야 한다.

### R2 복수 문서 제작 [요구]

여러 문서의 공통·차이에서 값 후보·공통 문구·블록 후보·위치·분기점을 추천하고, **어느 문서의 어떤 차이 때문인지** 보인다.

비교할 문서 묶음과 **출력 기준 문서는 사용자가 지정**한다. 첫 파일을 묻지 않고 기준으로 삼지 않는다. 사용자가 묶지 않은 문서는 한 템플릿으로 합치지 않는다. 사용자가 제공한 공고서 두 사례는 독립 사례로 유지한다.

공통·차이에서 찾는 것은 분기 **후보**까지이고, 그 차이가 어떤 업무 조건 때문인지는 사용자가 확인·입력한다.

- **결정(2026-10-05)**: HWPX 복수 문서 비교는 후순위(8.5, #81)이고 TXT 비교가 먼저다.
- [검토] Kordoc의 후보 탐지 원리를 참고해 예상 누름틀·앵커와 앵커+ 후보를 찾는다. 활용 범위는 확인하며 코드·의존성 도입과 원리 참고를 구분한다.

### R3 추천 표시와 확정 [요구]

추천은 초안이며 확정과 구분한다. 항목마다 문서, 원문 부위, 추천 이름과 현재 값, 종류(값/블록/분기), 근거를 보인다.

위치 표시는 형식별이다. **HWPX는 쪽·제목·원문 부위, TXT는 줄 범위·제목. 없는 정보를 만들어 붙이지 않는다.**

쪽·제목별로 묶고 ‘유지할 것 고르고 나머지 한 번에 제외’, 되돌리기, 원문 이동, 수동 추가, 이름·연결 수정, 확정을 제공한다. TXT에서는 줄 범위·제목을 사용한다. **추천 제외는 원문 삭제가 아니다.**

**결정(2026-10-05)**: 추천 목록은 한 줄 표시다. 유지/제외는 체크(체크 = 유지, 빈 체크 = 제외), 종류는 색으로 구분하고 글자 표지는 8절의 약자(입력·블록·분기·위치)를 쓴다. 값은 한 줄로 자르고 고르면 두 번째 줄에 전체 값과 위치가 보인다. 입력 항목 추천과 제목별 블록 후보(#78)는 같은 목록에 들어간다(8.4, 8.6 정리 3).

### R4 영역 지정과 이름 [요구]

주석 달듯 드래그·선택 → 항목 추가 → 이름 정하기 → 데이터 연결 → 결과 확인으로 이어진다. 이름을 정하는 경로는 다음 세 가지다.

1. 문서 라벨·제목·문맥에서 추천.
2. JSON·DB·XLSX 컬럼 중 선택.
3. 직접 입력.

누름틀 이름은 가급적 데이터 원천 이름과 일치시킨다. 이름이 원천 키와 같으면 연결 **후보를 자동으로 맞춘다**. 승인은 별도 동작이다(R10). **표시 이름·원천 키·문서 위치는 각각 저장**하며, 표시 이름을 바꿔도 원천 키는 바꾸지 않는다.

의미 기반 추천의 정확도는 별도 검증 대상이다. [검토] 향후 Jev 활용은 [미정]이다.

**결정(2026-10-05)**: 범위 선택은 두 방식이다. 드래그로 블록 선택, 시작·끝 깃발 찍기(결정 6).

### R5 데이터 연결과 업무 건 [요구]

원천·컬럼·선택 건의 실제 값·연결 여부·문서 위치를 한 화면에서 본다. 업무 건을 바꾸면 값과 문서 결과가 함께 바뀐다.

업무 건을 바꾸는 동안 **‘갱신 중’**을 표시하고, **현재 건과 일치하는 결과만 내려받을 수 있다. 이전 건의 결과가 섞여 보이지 않는다.**

DB 종류·직접 접속·XLSX 복잡 서식 범위는 [미정]이다. 미정인 데이터 접속 범위를 임의로 넓히지 않는다. 단, G2B Helper DB에는 직접 접속하지 않고 Helper가 라벨–값 JSON을 넘긴다(8.9의 14, 2026-10-07 확정).

**Helper 쪽 요구(2026-10-07, 8.9의 14. Studio 구현 범위가 아니다)**: Helper의 "문서/문서 생성" 칸에서 자료를 고르면 라벨–값 JSON을 넘긴다 → 같은 이름 `{{필드}}`는 자동 연결, 다른 이름은 한 번 연결해 저장 → 타입·표시 형식 반영(금액 쉼표, 문서에 "원"이 있으면 중복 금지, 날짜는 지정 형식, 전화·식별번호는 앞자리 0을 보존하는 문자) → 새 파일로 저장. 텍스트 템플릿 경로(선택 → `{{필드}}` 치환 → 수정·복사)도 같은 칸에 둔다. 템플릿에만 있는 키는 알리고 DB에 남는 키는 무시한다. Helper DB를 정리하기 전까지는 JSON 연결부에서 보정한다. Studio가 맡는 것은 `/api/g2b` 계약([엔진 명세](../../../docs/engine-spec.md) 8.8.14)과 `/quick` 실사용 한 바퀴뿐이다.

### R6 블록과 분기 [요구]

블록은 재사용·선택에 맞는 크기로 만들며 번호 제목 전체를 강제하지 않는다. 기본 이름은 내용 제목 또는 서로 구분되는 번호 이름으로 만들고 사용자가 바꿀 수 있다.

분기 화면에서 **위치 × 경우 → 선택 블록 → 순서**가 한눈에 보이고, 현재 선택·미선택·결과 위치가 드러난다. 조건 자동 선택과 수동 선택을 구분해 표시하고, 확정한 수동 선택을 자동으로 바꾸지 않는다.

분기점 하나당 블록 **하나**다(현재 엔진 계약 8.8.6). **재확인 필요·동률은 생성 차단**이다. 두 분기점에 각각 작은 블록을 고르는 것으로 대부분을 해결한다. **한 자리에 여러 블록 + 순서**는 후순위다(8.5, #82). 여러 블록이 필요하면 분기점을 여러 개 두고 분기점 순서로 정한다. 하위 분기·블록 안 블록은 [미정]이다. 화면 시안에서 미정인 다중 선택 계약을 먼저 구현하지 않는다.

**결정(2026-10-05)**: 블록은 블록 자신의 서식까지 가져오는 것이 기본이다. 넣는 자리의 문단 서식과 다르면 "서식이 다릅니다, 확인하세요"로 표시만 하고 자동으로 바꾸지 않는다. 사용자가 결과를 고친 뒤 그 부분만 다시 파싱해 블록으로 저장할 수 있다(결정 3). 블록 안 입력 항목 이름은 문서의 같은 이름 항목이며, 같은 이름이 여러 곳이면 전부 같은 값이다(누름틀 정책과 동일, 결정 4). 공용 블록은 판을 가진다(언제·무엇이 바뀌었는지). 템플릿이 옛 판을 쓰면 "최신 판 있음"을 알리되 자동 교체하지 않는다(결정 5).

### R7 편집과 미리 보기 [요구]

선택 항목에 집중해 편집하고 원래 위치·스크롤로 돌아온다. 닫을 때 작성 중 내용을 조용히 버리지 않는다. 블록으로 만든 뒤에도 편집 가능 범위를 확인해 반영한다. Ctrl+Z가 글·필드 삽입·블록·조건 변경에 일관되게 동작한다.

**선택 승계**: 같은 업무 건 안에서 데이터가 바뀌어도 확정한 수동 선택은 유지한다. **다른 업무 건으로 옮길 때는 묵시적으로 승계하지 않고**, **‘이전 건의 선택 복사’**를 명시 동작으로만 둔다. 복사된 선택의 유효성은 기존 템플릿·블록 내용 및 재확인 계약을 따른다.

**편집 동작**: 집중 편집은 **닫기 / 취소 / 초안 보관 / 템플릿(공용 블록)에 반영 / 이번 건에만 반영**을 구분한다. **이번 건 수정이 공용 블록·템플릿을 바꾸지 않는다.** 템플릿과 공용 블록 원형은 같은 저장 범위가 아니며, 반영 대상을 구분하고 각 대상의 기존 저장·전파 계약을 따른다. 값은 데이터 항목 단위이고 "이번 건 보완"은 블록 문구 단위다(8.6 정리 6).

| 형식 | 요구되는 편집·확인 흐름 |
| --- | --- |
| TXT | 본문·블록 직접 수정과 결과 생성 |
| HWPX | 원문 위치를 보며 지정·지원되는 편집·결과 확인 |
| MD | 보조 형식 |

HWPX의 **값 변경 / 문단 편집 / 블록 교체 / 표·서식 자유 편집**은 지원 여부를 나눠 표시한다. 이를 모두 지원한다고 표시하지 않는다. 원본은 보존하고 결과는 별도로 만든다.

### R8 반복 생성 [요구]

템플릿 선택 → 업무 건 → 블록 선택 → 보완 → 바로 생성 또는 미리 보기 후 생성으로 이어진다. **미리 보기는 값·블록·순서가 반영된 결과**다. 저장한 템플릿을 다른 업무 건에도 재사용하며 매번 분석·연결을 반복하지 않는다.

일괄 생성 규모·조작은 [미정]이다.

### R9 화면 [요구]

쉽고 간단하며 동선을 최소화하고 안내는 필요한 순간에 제공한다. 초기 선택(문서·데이터 원천)은 접고 요약만 남긴다. 문서가 중심 공간이며 분기·참조 목록은 일정 이상 보인다. 접힌 곳에 무엇이 있는지 알 수 있어야 한다.

상단은 작은 메뉴·도구줄(열기·최근·저장·생성), 확대율·줄 위치는 하단 상태줄에 배치하고 내부 주소(구역·오프셋)는 보이지 않는다. **1366×768·1024×768**에서 동작해야 한다.

[현재 생각] VS Code·Cursor·Codex·Obsidian의 접기·집중 편집·선택 상세·위치 유지 방식을 참고한다. 특정 제품의 외형을 그대로 복제하는 요구는 아니다.

**결정(2026-10-05)**: 배치는 A(문서 중심 + 옆 상세)다(권고 수용). 세부 화면 결정은 8.4, 화면 계약은 [스튜디오 명세](../../../docs/studio-spec.md) 4c절.

### R10 안전 [요구]

승인 안 된 후보 미주입, 이중 치환 금지, 중복 매핑 거부, 오래된 결과 내려받기 차단을 유지한다. 지원 안 되는 작업은 이유를 보인다. 이름 일치·추천·후보 승격을 승인과 혼동하지 않는다. 사용자의 원본 문서와 원본 데이터는 덮어쓰지 않는다.

## 4. 검토 후보와 미정 사항

### 4.1 편집 배치 — 결정됨(2026-10-05)

| 대안 | 비교할 내용 |
| --- | --- |
| 문서 중심 작업창 + 선택 시 옆 상세 | HWPX의 기본 후보. 원문 위치를 보며 선택하고 뷰어는 접을 수 있음 |
| 블록 집중 편집(확대창) | 블록 수정 때 열고 닫으면 원래 선택·스크롤로 복귀. TXT·HWPX 공통 |
| 블록 삽입 때만 뷰어 | TXT 후보. 평소 한 창 편집. 본문 편집창에서 위치 선택이 가능하면 별도 뷰어 필요성도 비교 |
| 단계별 화면(추천→편집→생성) | 처음 쓰는 사람에게 유리할 수 있음. 제작 흐름에만 적용하는 후보 |
| 원문·결과 병행 | 미리 보기 단계에서 전환 또는 병행하는 후보 |
| 중앙 vs 오른쪽 편집 | 고정하지 않음. 같은 독립 사례와 같은 작업으로 왕복 횟수·보이는 양·위치 복원을 비교 |

검토 권고는 **HWPX: 문서 중심 + 옆 상세 + 블록 확대 편집**, **TXT: 한 창 편집 + 삽입 때만 필요한 위치 안내/뷰어**였다. 2026-10-05에 사용자가 A(문서 중심 + 옆 상세)를 채택했다(권고 수용, 근거는 #60 댓글의 시안·실행 화면 채점). B(편집 중심)는 선택하지 않았다. 위 표는 비교 기록으로 남긴다.

분기는 **경우를 열, 분기점을 행으로 한 표**에 선택 블록과 순서를 적는 형태를 먼저 시안으로 본다. 업무 조건의 모든 조합을 무조건 펼치는 방식을 확정하지 않는다. 필요한 경우를 등록한 표와 조건으로 좁혀 보는 표를 비교할 수 있다. [검토]

### 4.2 편집 기술 [미정·검토]

HTML 편집기 + HWPX 처리 / rhwp 편집 모드 / txt→txt는 비교 대상이다. 확인할 것은 선택 위치↔생성 대상 연결 안정성, 블록 재편집·재적용, 글 수정과 구조·서식 편집의 지원 범위, 미리 보기와 저장 파일 일치, 미지원 안내다.

**rhwp는 현재 계약대로 읽기 전용**이다. 편집 모드는 **왕복 보존 비율 측정 뒤 후보로만** 다룬다. 검토 후보라는 이유로 편집·직렬화 API를 사용하지 않는다. **Kordoc은 원리 참고와 의존성 도입을 구분**한다. 새 편집기나 의존성 도입을 이 요구 문서에서 승인하지 않는다.

[검토·후순위, 2026-10-07] 한글 편집창을 Studio 창 안에 넣는 방식(한컴 개발자 포럼 1497번 답변의 "부모 창 지정")은 Windows 데스크톱 연결이 필요하다. rhwp를 바꾸는 것이 아니라 작은 시험 화면(넣기 → 선택·입력 → 저장 → 다시 열기 → 새 문서 전환)으로 먼저 확인한다(8.9의 11).

### 4.3 계약 결정 대기

- TXT·MD 조건 입력 문법과 엔진 9절의 연결은 [#58](https://github.com/SJO1231/HWPX-Studio/issues/58)에서 결정한다. **계약 결정 전에는 보류한 text-template.ts 및 연결 변경 stash를 꺼내지 않는다.**
- 한 자리에 여러 블록+순서는 후순위(8.5, #82)다. 하위 분기·블록 안 블록은 계약 담당자가 비교한다(미정). rhwp 편집창은 후순위(#80)다.
- DB 종류·복잡 XLSX, 일괄 생성 규모·조작, Jev 도입과 의미 추천 정확도 목표는 미정이다. G2B Helper DB 직접 접속은 하지 않는다(Helper가 라벨–값 JSON 전달, 8.9의 14, 2026-10-07 확정).

## 5. 확인 기준과 근거 구분

다음 인수 확인은 **실제 자료로** 한다. 사용자 자료는 읽기 전용이며 두 독립 공고서 사례를 임의로 묶지 않는다. 복수 제작 확인에는 사용자가 별도로 지정한 비교 문서 묶음과 기준 문서가 필요하다. 자료가 부족하면 미검증으로 남긴다.

| A5 | 업무 건 교체 시 값·문서 동시 갱신, 갱신 중 표시, 오래된 응답·다운로드 차단 |

합성 회귀와 필수 `npm run verify`는 별도로 유지한다. 구현 PR은 검사 명령·수치·미검증 범위를 적는다. 실제 자료의 파일 이름·본문·값·개인 경로·토큰을 코드·문서·이슈·PR에 싣지 않는다. 근거는 비식별 해시·수량·판정으로 기록한다.

### 8.2 주 흐름 — 블록 중심

1. **주 흐름은 블록 중심이다.** [2026-10-05 · 확정 요구] 사용자는 문서를 처음부터 쓰지 않고 이미 검토된 공고서에서 복사해 쓴다. 그래서 제품의 주 흐름은 "문서에서 범위를 정해 블록으로 저장 → 블록 저장소에 모음 → 바탕 문서의 분기점에 블록을 갈아끼워 생성"이다. 빈 문서에서 글을 쓰는 흐름이나 Markdown 중심 입력은 주 흐름이 아니다.
2. **문서 전체를 한 번에 블록으로 나누는 것도 같은 기능의 반복이다.** [2026-10-05 · 확정 요구] 별도 모드를 두지 않는다. 대신 "제목별 자동 나누기 제안"(엔진의 제목 범위 계산 이용)으로 블록 후보를 만들어 사용자가 체크로 고르게 한다. 제안은 후보일 뿐이며 사용자가 고르기 전에는 블록이 되지 않는다.
3. **1차 범위는 물품 공고서 바탕 문서 1개다.** [2026-10-05 · 확정 요구] 용역·공사는 뒤에 바탕 문서를 추가한다. 블록 저장소는 바탕 문서 종류와 상관없이 공용이다. 즉 물품에서 뗀 블록을 뒤에 용역 바탕 문서에도 넣을 수 있다.
4. **TXT(내부 기안문)는 같은 모델을 쓰되 가장 가벼운 화면을 쓴다.** [2026-10-05 · 확정 요구] 바탕 글 + `{{항목}}`이 기본이고, 블록·분기는 필요한 문서에만 쓴다. 뷰어 없이 한 창에서 편집하고 결과를 복사한다. 조건 규칙은 엔진 공통 규칙(#58에서 결정)을 쓰며 TXT만의 문법을 따로 만들지 않는다. Markdown은 보조 형식이다.

### 8.3 블록의 서식·이름·버전

1. **블록을 다른 문서에 넣을 때는 블록 자신의 서식을 유지하는 것이 기본이다.** [2026-10-05 · 확정 요구] 넣는 자리의 문단 서식과 비교해 다르면 "서식이 다릅니다, 확인하세요"라고 표시만 하고 자동으로 바꾸지 않는다. 자동으로 바꾸면 검토된 조항의 모양이 조용히 달라져 사용자가 알아채기 어렵기 때문이다. 사용자가 결과를 고친 뒤 그 부분만 다시 파싱해 블록으로 저장할 수 있다.
2. **"내용만 가져오기"와 "원본 페이지 설정 적용"은 후순위로 기록만 한다.** [2026-10-05 · 후순위] 엔진이 구역 설정 문단을 조각에서 제외하므로 설계가 더 필요하다(8.5 참조).
3. **블록 안의 입력 항목 이름은 문서의 같은 이름 항목과 같은 것으로 취급한다.** [2026-10-05 · 확정 요구] 같은 이름이 여러 곳이면 전부 같은 값이다. 누름틀이 같은 이름이면 같은 값을 받는 한글의 정책과 같다. 값은 **데이터 항목 단위**이고, "이번 건 보완"은 **블록 문구 단위**다. 둘을 혼동하지 않는다(8.6 정리 6).
4. **공용 블록은 버전을 가진다.** [2026-10-05 · 확정 요구] 언제, 무엇이 바뀌었는지가 남는다. 템플릿이 옛 버전을 쓰면 "최신 버전 있음"을 알리되 자동 교체하지 않는다. 바탕 문서가 바뀐 경우도 같다(템플릿에 적힌 원본 해시 대조로 감지). 사용자가 업데이트를 누르면 새 버전으로 다시 만들고 오류 검사(자리 못 찾음, 이름 충돌, 서식 차이)를 한다. 업데이트본을 저장할지 매번 새로 만들지는 사용자 자유다.
5. **분기점 하나에는 블록 하나만 고른다.** [2026-10-05 · 확정 요구, 엔진 계약 8.8.6] 여러 블록이 필요하면 분기점을 여러 개 두고 분기점의 순서로 순서를 정한다. "한 자리에 여러 블록"은 후순위로 기록한다(8.5).
6. **제작 모드에서는 분기점에 후보 블록을 갈아끼운 모습을 각각 미리 볼 수 있다.** [2026-10-05 · 확정 요구] 템플릿을 확정하면 사용 모드에서는 그 조건에 확정된 블록만 보이고, 다른 후보는 "변경"을 눌러야 나타난다. 사용 모드에서 후보를 다 늘어놓으면 고를 일이 없는 사람에게 정보만 많아지기 때문이다.

1. **배치는 A(문서 중심 + 옆 상세)다.** [2026-10-05 · 권고 수용] 정적 시안 A·B 채점과 실제 공고서로 돌린 실행 화면 시험(#60 댓글)에서 A가 항목당 왕복 횟수와 스크롤 복원에서 앞섰다. B(편집 중심)는 선택하지 않았다.

### 8.6 정리 — 겹치거나 두 갈래로 읽히던 말을 하나로

| 1 제작/사용 모드 | "제작 흐름·사용 흐름"(흐름)과 "제작 모드·사용 모드"(화면)로 따로 말했다 | **모드** 하나로 부른다. 메뉴 구조는 하나이고 열기의 시작점(새 템플릿 / 저장한 템플릿)으로 갈린다 | 흐름과 모드가 같은 것을 가리켰고, 화면 두 벌을 만드는 것으로 오해될 수 있었다 |
| 2 자리당 블록 하나 / 자리 여러 개 | "분기점 하나에 블록 하나"와 "한 자리에 여러 블록 + 순서"가 나란히 있었다 | **분기점 하나에 블록 하나**. 여러 블록은 분기점을 여러 개 두고 분기점 순서로 정한다. 한 자리 다중 블록은 후순위 | 엔진 계약이 하나이고, 분기점 여러 개로 대부분 해결되므로 계약을 둘로 늘릴 이유가 없다 |
| 3 추천 목록 하나 | 입력 항목 추천 목록과 제목별 블록 후보 목록을 따로 생각했다 | **한 목록**에 종류 약자(입력·블록·분기·위치)로 구분해 넣는다 | 목록이 둘이면 같은 원문 위치가 두 곳에 나와 혼란스럽고, 체크·제외·되돌리기 조작을 두 번 만들게 된다 |

### 8.7 계획과 첫 조각 합격 기준

- **첫 구현 조각**(2026-10-05 · 확정 요구): 물품 공고서 바탕 문서 1개를 열고, 다른 공고서에서 조항 블록 2~3개를 떼어 저장소에 저장하고, 바탕 문서의 분기점에 갈아끼워 생성한 결과를 한컴에서 확인한다. 이 한 바퀴가 돌면 통과다. 입력 항목 연결·분기 조건(경우)은 그다음 조각이다.
- **제목별 블록 후보 제안(#78)은 M1 보조다.** [2026-10-05 · 확정 요구] 첫 조각 합격 기준에는 들어가지 않는다.
- **미연결 자리 기본 방침은 "오류"다.** [2026-10-05 · 확정 요구] 생성 전에 연결 안 된 자리 수를 보여 주고 생성을 막는다. 템플릿별로 "자리 유지"로 바꿀 수 있다(#67).
- 마일스톤: M1 "LITE 1차 — 블록 한 바퀴"(첫 조각만), M2 "LITE 2차 — 입력 항목·경우·사용 모드", M3 "후순위 기록". 엔진 선행 과제·화면 과제·순서·기간은 [작업 기록](../../../docs/task-record.md)의 첫 조각 계획을 따른다.
- 실제 문서의 파일명·원문·개인 경로는 어떤 문서·이슈·PR에도 적지 않는다. 식별은 SHA-256 앞 10자다.
