## 0. 설계자에게 먼저 드리는 요청

사용자는 비전문가이며 원하는 업무 흐름을 설명하는 과정에서 구체적인 기술 용어와 구현 방법도 함께 제시했다. 따라서 이 문서의 모든 기술 수단을 확정된 설계로 받아들이지 말아 달라. **반복적인 HWPX 문서 작성에서 값과 선택 문구를 안전하게 바꾸고, 사용자가 결과를 확인할 수 있게 한다**는 목적을 기준으로 검토해 달라.

현재는 실행 가능한 로컬 MVP가 있다. 그러나 실제 자료에서 차단되는 문서가 많고, 별도 코드 리뷰에서 승인 우회와 오주입 문제가 확인되었다. 현 상태를 업무 사용이 검증된 완성품으로 전제하면 안 된다.

다음 사항에 대해 의견을 요청한다.

1. 요구를 기술적으로 가능한 범위와 어려운 범위로 나누고, 어려운 이유를 구체적으로 설명해 달라.
2. 두 엔진과 공통 템플릿 개념이 적절한지 검토하고, 더 단순한 대안이 있으면 비교해 달라.
3. 현재 자산 중 재사용할 부분과 고칠 부분을 구분해 달라. 전면 재작성은 필요성이 입증될 때 제안해 달라.
4. 데이터 정확성·사용자 승인·원본 보존을 우선하여 최소 실행 순서를 제시해 달라.
5. 판단에 부족한 정보, 먼저 수행할 작은 실험, 각 실험의 합격 기준을 명시해 달라.

이 문서는 검토 의뢰 자료다. 아래의 보완 설계와 단계 계획은 제안이며, 사용자 승인이나 구현 완료를 뜻하지 않는다. 외부 설계자에게 문서나 원본 자료를 실제 전송한 상태도 아니다.

## 1. 근거와 읽는 방법

### 1.1 근거의 범위

이번 세션에 제공된 사용자 발언, 프로젝트 소스, README, 검증 상태 기록, 저장된 시험 보고서를 대조했다. 사용자 발언의 의미를 정리한 문서이며 대화 원문 전체를 그대로 복제한 속기록은 아니다. 초기 요청에 등장하는 ‘기존 세션에서 정의한 방식’ 중 이번 대화나 파일로 확인할 수 없는 내용은 별도로 복원했다고 가정하지 않는다.

다음 표시를 구분한다.

| 구분 | 의미 |
|---|---|
| 사용자 요구 | 이번 세션에서 사용자가 직접 요청한 방향·기능·제약 |
| 해석 | 여러 발언에서 도출한 업무 문제 또는 의미 정리. 사용자의 직접 진술과 구분 |
| 구현 확인 | 현재 소스·화면 흐름·문서에서 확인되는 기능. 모든 입력에 대한 정상 동작을 뜻하지 않음 |
| 실행 확인 | 지정된 입력과 검사에서 실제 확인한 결과 |
| 제안 | 아직 구현·검증되지 않은 해결 방법 또는 설계 보완 |
| 미확인 | 근거가 부족하거나 시험하지 않은 사항 |

### 1.3 서브에이전트 검토 절차

1. **요구 분석 담당:** 사용자 발언과 현재 문서를 대조하여 페인포인트, 요구, 구현 수단, 충돌 가능성을 분리한다.
2. **기술 근거 담당:** 소스·보고서를 읽어 구현 범위, 시험의 증명 범위, 결함과 해결 가설을 정리한다.
3. **통합 담당:** 두 결과를 결합해 하나의 문서로 작성하고 수치·표현·근거 링크를 확인한다.
4. **재검토:** 통합 문서가 미구현 기능이나 가설을 사실로 쓰지 않았는지 교차 검토한다.

각 서브에이전트는 읽기 전용으로 검토했고 제품 코드를 수정하거나 별도 설계 파일을 만들지 않는다. 이는 한 세션 내 역할 분담 검토이며 외부 전문가의 독립 검증을 받은 것은 아니다.

## 3. 해결하려는 문제

아래 페인포인트는 요구에서 도출한 해석이다. 실제 작업 시간, 월 문서량, 오류율, 사용자 인터뷰로 측정된 수치는 없다.

| 페인포인트 해석 | 사용자에게 필요한 결과 | 대응 기술 후보 | 확인할 지표 |
|---|---|---|---|
| 비슷한 공고서를 복사해 여러 값을 반복 수정해야 함 | 한 레코드를 고르면 여러 위치의 값이 일관되게 바뀜 | Field 매핑, 승인된 위치에 주입, 생성 후 재읽기 | 기대값·반복 횟수 일치, 다른 레코드 값 혼입 0 |
| 어떤 부분이 고정·변수·선택 문구인지 매번 판단해야 함 | 기존 문서를 활용해 검토 가능한 후보를 얻음 | 유사 문서 비교, 누름틀·라벨·문맥 기반 후보 | 후보의 정밀도·재현율 및 사용자 수정 시간 |
| 참가자격 등 긴 문구를 상황에 맞게 고르기 어려움 | 조건 추천 후 직접 선택하고 내용을 확인 | Block Group, 조건, 추천 이유, 수동 선택 우선 | 기대 Block 선택, 선택 이유 표시, 수동 선택 유지 |
| 표나 글자 서식이 망가질까 불안함 | 필요한 곳을 바꾸면서 나머지 구조·서식 보존 | 원본 복제, 제한된 범위 편집, 자원 재매핑 | 변경 영역 외 보존, 한컴 열기, 정한 배치 기준 |
| DB와 문서의 이름·표시 방식이 달라 매핑이 어려움 | 금액 등 값이 같은 항목을 추천받고 수정 | 값 정규화, 샘플 대응, 명시적 열 매핑 | 독립 정답 매핑과 대조, 모호한 후보 자동 확정 금지 |
| 자동화가 맞게 동작했는지 판단하기 어려움 | 적용 전후 비교와 실제 생성물 확인 | Template/Data/실제 HWPX Preview, 검증 결과 | 구조·데이터·승인·시각 검사를 각각 구분 |

## 4. 지켜야 할 방향과 재검토 가능한 방법

### 4.1 사용자 요구의 중심

- 단순 문서는 빠르게 만들고, 복잡한 기존 문서는 가능한 한 원본 서식을 보존한다.
- 동일하거나 유사한 두 문서 이상을 분석해 템플릿 작성의 수작업을 줄인다. 빈 템플릿부터 직접 작성하거나 JSON/Excel 등 원데이터에서 시작하는 경로도 고려한다.
- 자동 분석·추천을 즉시 반영하지 않고 Grid에서 수정·병합·확정한다.
- 데이터 선택과 Block 선택 후 적용하면 치환 전 템플릿과 치환 후 결과를 확인한다.
- 사용자 직접 선택이 추천보다 우선한다. Jev에게 XML 구조 처리나 최종 결정을 맡기지 않는다.
- 기존 Core·Filler·Anchor·Kordoc 자산을 우선 재사용하고 RHWP는 읽기 전용 뷰어로만 쓴다.
- 사용자 원본을 덮어쓰지 않고 생성 결과를 검증한다. 변경 뒤 이전 생성물을 최신 결과처럼 제공하지 않는다.
- 현실 샘플·복잡한 사례를 포함해 데이터가 실제로 올바르게 주입되었는지 확인한다.

### 4.2 설계자가 대안을 제안해도 되는 부분

현재 TypeScript 구현을 유지하는 것이 경제적인지, Python 일부를 연결할 이득이 있는지, 두 엔진을 동시에 확대할지 순차적으로 안정화할지는 검토 대상이다. Grid의 상세 구성, 조건 표현, ID·별칭 설계, Anchor 재탐색, 추천 모델 도입 시점도 검토 대상이다.

‘Jev’는 현재 요구에서 추천 역할을 가리키는 이름이다. 이 세션에서는 외부 Jev 서비스의 API·모델·운영 계약을 정의하지 않았다. ‘Jev 연동 완료’로 읽으면 안 된다.

사용자가 지정한 Jev 역할은 **Field 이름 추천, Field 중복 후보 판단, DB Column Mapping 추천, Block/In Template 추천, Anchor 재탐색 보조**다. XML 구조 처리·최종 승인·Anchor+ 자동 확정은 맡기지 않는다. 현재 구현이 다섯 역할을 모두 제공한다는 뜻은 아니다.

### 4.3 초기 범위에서 제외한 사항

완전한 한글 WYSIWYG, 복잡한 표의 완전한 Markdown 재현, 모든 서식의 MD↔HWPX 왕복 변환, Jev의 완전 자동 결정, Anchor+ 완전 자동 생성, 모든 HWPX 호환은 초기 제외 대상이다.

단순 반복 Block은 최초 요구에 포함되지만 반복 데이터 모델과 정확한 동작은 정의되지 않았다. 같은 Field를 여러 곳에 쓰는 기능과 배열의 각 행으로 표·문단을 반복 생성하는 기능을 구분해야 한다. 후자는 현재 미구현이다.

## 5. 개념을 프로그래머 관점에서 정리

| 개념 | 업무상 의미 | 현재 표현 | 설계 검토 포인트 |
|---|---|---|---|
| Field | 사업명·금액처럼 한 번에 바꾸는 단일 값 | `Field`의 id/name/column/format/targets/approved | 이름·ID·DB 열·문서 원문 토큰을 분리할 필요 |
| Anchor | 바꿀 위치 한 곳 | `Target.anchor`와 Core의 Word/Line/Field Anchor | 위치가 모호하거나 원문이 변하면 재확정 |
| Anchor+ | 선택 문구로 교체할 시작~끝 범위 | `Range`의 sourceId/from/to/group | 현재는 첫 구역의 연속 최상위 문단, 모든 XML 범위 아님 |
| In Template | 삽입할 내부 템플릿 | `Block` | MD 내용 또는 HWPX Fragment라는 서로 다른 표현을 가짐 |
| Block Group | 같은 목적을 가진 대안 묶음 | `Block.group`, 선택된 Block ID | 참가자격 그룹에서 일반·중소기업·직접생산 중 선택 |
| alias | 사용자가 알아보기 위한 별칭 | `Block.alias` | 별칭 변경으로 ID나 참조가 바뀌지 않아야 함 |
| Mapping | Field와 레코드 열의 연결 | `Field.column` | 값이 같다는 이유만으로 의미가 같다고 확정하지 않음 |
| Recommendation | 이름·매핑·Block 등의 제안 | 현재 로컬 규칙 결과 | 제안 근거와 적용 여부를 분리 |

현재 모델은 `Field.kind`에 field/block/fixed를 함께 담는다. 이는 후보 Grid의 분류를 간단히 표현한 구현이지, 고정 문구와 Block이 모두 단일 값이라는 뜻은 아니다. 이 모델을 유지할지 후보 모델과 확정 모델을 분리할지는 설계자의 판단을 요청한다. 즉시 큰 클래스 계층을 추가할 필요는 없다.

### 5.1 보완 제안: 한 값이 네 가지 역할을 겸하지 않게 한다

예를 들어 화면 이름은 `계약금액`, 내부 ID는 `field-…`, 데이터 열은 `예정금액`, 문서의 원래 토큰은 `{{추정가격}}`일 수 있다. 네 항목은 같을 필요가 없다. 표시 이름을 바꿨다고 다른 Field의 값이 덮어써져서는 안 된다.

또한 원시 숫자 `120000000`, 비교용 숫자 `120000000`, 출력 문자열 `120,000,000원`을 구분한다. 조건은 숫자로 평가하고 표시 형식은 출력 시점에 적용하는 방향이 적절하다. 정확한 금액 표현·허용 범위·빈 값 정책은 별도로 고정해야 한다.

### 5.2 보완 제안: 승인 경계를 엔진 전체에서 일치시킨다

추정 후보 → 사용자 확인 → 확정된 위치·매핑·Block → 생성 계획 → 결과 검증의 순서를 유지한다. Master에서만 승인 검사를 해서는 부족하며 가져온 Fragment도 같은 경계를 따라야 한다.

직접 작성한 Markdown의 명시적 변수와 기존 문서에서 추정한 후보를 어떻게 승인할지는 정책을 정해야 한다. ‘직접 작성했으므로 템플릿 등록으로 승인된 것’으로 볼 수는 있지만, 추정 후보가 이 경로를 통해 승인 없이 유입되면 안 된다.

## 6. 사용 흐름: 준비 단계와 반복 생성 단계를 분리

매번 다문서 비교와 Grid 확정을 다시 하게 만들면 반복 업무를 줄인다는 목적과 충돌한다. 아래는 기존 요구를 두 단계로 정리한 제안이다.

### 6.1 최초 템플릿 준비

시작 경로는 ① 유사 문서 비교 ② 빈 템플릿 직접 작성 ③ JSON/Excel 등 원데이터에서 열·타입 후보를 확인하고 템플릿 작성으로 구분한다. ③의 자동 템플릿 생성 수준은 원래 요구에서 구체적으로 정의되지 않았다. 데이터만으로 원본 HWPX의 서식이나 업무 문구를 복원할 수 있다는 뜻은 아니다.

| 단계 | 입력·사용자 행동 | 시스템 처리 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
| 1 | 최소 서식형/원본 서식형 선택 | 모드별 가능한 범위 안내 | 지원하지 않는 변환을 암시하지 않음 |
| 2 | 빈 MD 작성, 유사 문서 2개 이상 또는 원데이터 입력 | 입력에 맞는 후보 분석·작성 보조 | 원본 보존, 파싱 실패 구분, 데이터만 있을 때 서식 추정 한계 안내 |
| 3 | 필요하면 샘플 데이터 입력 | 문서 A↔행 A 등의 대응 확인·매핑 추천 | 대응 관계와 모호성 표시 |
| 4 | Grid에서 이름·종류·매핑·범위 수정·병합 | 후보를 확정 상태로 전환 | 충돌·중복 이름·누락 데이터 정책 확인 |
| 5 | Anchor+와 Block Group 구성 | 별칭·조건·우선순위·기본 Block 저장 | 범위 중첩·지원 불가 구조 거부 |
| 6 | 대표 레코드로 미리보기·생성 검증 | 값·Block·구조·렌더 확인 | 정한 시험을 통과한 템플릿 버전만 재사용 |

### 6.2 반복적인 문서 생성

1. 저장된 템플릿과 데이터 레코드를 선택한다.
2. 조건 또는 추천에 따른 기본 Block과 이유를 확인한다.
3. 필요하면 Block을 직접 바꾼다.
4. **적용**을 누른다.
5. Template Preview와 Data Preview를 비교하고 실제 생성 HWPX를 확인한다.
6. 검증 결과가 허용 기준을 만족하면 새 파일로 저장한다.

데이터·매핑·범위·Block이 바뀌면 이전 생성물은 무효화한다. 원본 내용이나 위치 근거가 바뀐 템플릿을 계속 사용할 수 있는 조건도 정해야 한다. 현재 UI는 주요 상태 변경 시 출력 무효화를 구현했지만 모든 편집·복원 경로의 완전성까지 증명한 상태는 아니다.

### 6.3 사용자가 기대하는 한 번의 적용 예

데이터 레코드가 사업명 `전산장비 구매`, 계약금액 `120000000`, 중소기업 `true`, 직접생산 `true`라고 가정한다. 조건 `중소기업=true AND 직접생산=true`로 qualification 그룹의 direct-production Block을 추천하고 사용자가 그대로 적용하거나 다른 Block으로 바꾼다.

| Template Preview | Data Preview |
|---|---|
| `{{사업명}}` | 전산장비 구매 |
| `{{계약금액}}` | 120,000,000원 |
| `[IN_TEMPLATE:qualification]` | 실제 선택된 참가자격 문단 |

원본 서식형에서는 같은 qualification 선택을 확정된 Anchor+ 범위의 Fragment 교체에 연결한다. 이 예는 목표 흐름의 설명이다.

처음 제시한 화면 구상은 왼쪽에 DB·Template·Block Group·Block·조건, 가운데에 Markdown 편집기, 오른쪽에 추천·적용 Block·Preview를 두는 것이다. 원본형의 가운데 화면과 범위 선택 방식은 지원 기능에 맞게 달라질 수 있다. 조건을 표로 편집하는 UX는 원하는 수단이며, 현재의 제한된 조건식 편집이 그 요구에 충분한지 검토해야 한다.

## 7. 두 엔진의 역할과 선택 이유

아래는 두 엔진이 지향하는 논리적 처리 순서다. 현재 구현에는 10절의 승인·재치환 결함이 남아 있으므로 이 흐름의 모든 보장이 구현되었다는 뜻은 아니다.

### 7.1 최소 서식형

```text
Main Markdown
→ Block 선택
→ In Template 삽입
→ 승인된 데이터 바인딩
→ Markdown/HTML Preview
→ Kordoc로 HWPX 생성
→ 검증·실제 HWPX Preview·저장
```

제목·문단·목록·간단한 표 중심의 새 문서에 적합한 경로다. 원본 HWPX를 Markdown으로 바꾸면 정밀한 서식 정보가 손실될 수 있으므로 원본의 완전한 왕복 편집 경로로 보지 않는다.

### 7.2 원본 서식형

```text
Master HWPX의 사본
→ 확정 Anchor+ 확인
→ 선택한 Fragment 삽입 및 참조 자원 처리
→ 변경된 구조에서 Field 위치 확인
→ 승인된 데이터 바인딩
→ 필요한 누름틀 Unwrap
→ 재파싱·값/구조/보존 검사
→ 실제 HWPX Preview·새 파일 저장
```

서식과 표·자원을 유지할 가능성은 이 경로가 높다. 다만 값이 길어지거나 문단이 늘면 줄바꿈과 쪽 수가 달라지는 것은 가능하다. ‘원본 서식 보전’이 모든 데이터 길이에 대한 동일 픽셀·동일 쪽 수 보장은 아니다. 허용할 변화의 범위를 정해야 한다.

### 7.3 공통화할 것과 공통화하지 않을 것

공통화 대상은 Field의 의미, 데이터 매핑, Block의 선택, 사용자 승인, 검증 결과 표시다. MD와 Raw HWPX의 내부 표현이나 편집 연산까지 같게 만들 필요는 없다. 동일 UI는 기능의 배치·용어·버튼 흐름을 공유한다는 의미로 해석한다. 모드를 바꾸면 언제나 무손실 전환된다는 약속은 하지 않는다.

### 7.4 Preview 대안 비교

| 방법 | 장점 | 한계 | 현재 판단 |
|---|---|---|---|
| Markdown/HTML | 입력·값·Block 내용을 즉시 보기 쉬움 | 실제 HWPX 조판이 아님 | MD 편집 중 기본 Preview |
| HWPX 내 저장 Thumbnail | 기존 썸네일 표시가 간단할 수 있음 | 생성 후 재생성되지 않은 이미지는 최신 문서와 다를 수 있음 | 최종 결과 확인의 주 근거로 사용하지 않음 |
| RHWP 읽기 전용 | 실제 생성 바이트를 열고 표·페이지를 확인 | 한컴과 조판 차이 관측 | 현재 채택, 편집·직렬화 API 사용 금지 |
| 한컴에서 직접 열기 | 실제 사용 프로그램의 호환·본문 확인 가능 | 설치·실행 환경 필요, 단순 열기는 배치 품질 증명이 아님 | 대표 산출물의 별도 검증 |

현재 HTML+RHWP 선택은 기존 자산 재사용을 근거로 한 구현 판단이다. 설계자는 더 단순한 검증 방법이 있는지 의견을 제시할 수 있다.

## 8. 현재 구현과 미구현의 경계

| 항목 | 현재 확인된 상태 | 제한·남은 판단 |
|---|---|---|
| 런타임·UI | TypeScript Core, 표준 Node HTTP/SQLite, 브라우저 JS | Python·UI 프레임워크·별도 모델 서버 없음 |
| 기존 코드 재사용 | HWPX Studio의 분리된 TS Core 110파일을 해시 고정 | Filler 원본 전체를 이번에 독립 재검증한 것은 아님 |
| Python Anchor | 보관된 `hwpx_injector_explicit.py`를 참고 | 정확히 ‘Anchoring’이라는 별도 프로젝트 경로는 미확인 |
| MD 생성 | 설치된 Kordoc 4.18.2 사용 | 모든 서식 변환·정밀한 원본 복원 대상 아님 |
| 원본 생성 | Anchor·Fragment·자원 재매핑·주입·Unwrap 연결 | 현재 승인·데이터 관련 결함 있음 |
| 비교 Grid | 누름틀/placeholder 이름, 라벨, 인접 셀, 값 차이 활용 | 일반적인 구조 정렬·문맥 의미 분석 구현 아님 |
| Mapping | 정규화 값 비교, 사용자 열 수정 | 샘플 문서와 레코드 순서가 대응해야 함 |
| DB·Schema | JSON/CSV/XLSX 첫 시트, SQLite 프로젝트 이력, 샘플 JSON Schema | 외부 SQL DB 연결·관계형 DDL·전체 도메인 Schema 추론 아님 |
| 조건·선택 | AND와 비교 연산, 우선순위, 기본 Block, 수동 선택 | 점 경로 조건 결함, 복잡한 논리·중첩 규칙 미구현 |
| Jev | 근거를 표시하는 로컬 규칙 기반 0단계 | 의미 모델·임베딩·외부 Jev 연결 없음 |
| Anchor+ UI | 첫 구역의 연속 최상위 본문 문단 | 표 내부 일부 범위·임의 다중 구역 UI 미지원 |
| 반복 | 반복된 동일 Field 주입 일부 시험 | 배열 행 반복·중첩 In Template 미구현 |
| Preview | Template/Data/RHWP, 생성 바이트 렌더 | RHWP와 한컴 쪽 수 차이, UI는 첫 20쪽 |

현재 입력 제한은 문서 최대 20개, UI 파일당 10MB, HTTP 요청 32MB, 레코드 5,000행이다. XLSX는 저장된 셀 값·수식 결과를 읽으며 수식 재계산이나 날짜 서식의 완전한 해석을 하지 않는다. 이 제한은 제품 성능 보증 수치가 아니라 구현된 상한이다.

기준 프로젝트의 Git HEAD는 `523f35ffe73f6b035ce7627edee567135b5dc32c`지만 당시 미커밋 변경이 있었다. 실제 재사용 코드의 근거는 해당 HEAD와 동일하다는 추정이 아니라 E8의 개별 파일 해시다. 기준 프로젝트와 vendor 스냅샷을 임의로 수정하지 않는다.

## 9. 검증 결과를 해석하는 방법

### 9.1 복합 합성 시험

2026-10-02 기록에는 긴 MD 24개 레코드, 3개 Block Group, 100개 조항·15개 표 행, 여러 Anchor+, 중첩 표·그림·누름틀·머리말/꼬리말 사례가 포함된다. 성공 산출물 29건, RHWP 293쪽을 검사했다. 한컴에서는 대표 3개 파일 열기와 기대 본문 문자열 10개를 확인했다.

이 시험 과정에서 빈 금액→0 변환, 비유한 숫자, 표시 금액의 문자열 조건 비교, XLSX 누락·오류·시트 순서 등 7개 결함을 고쳤다. 합성 입력의 통과가 현실의 모든 문서 구조를 대표하지는 않는다.

### 9.2 실제 참고자료 공고서 시험

사용자가 말한 ‘참고자료’는 lite와 기준 HWPX Studio 폴더에서 찾지 못해 형제 프로젝트 `../DocWeave/참고자료`를 사용한다는 가정을 알렸다. 사용자가 이 경로를 명시적으로 확정했다는 근거는 없다.

| 범위 | 결과 | 해석 제한 |
|---|---|---|
| 파일 수 | 공고서 이름을 포함한 HWPX 55개, 해시 중복 제거 후 35종 | 실제 기입 문서·표준 양식·연습 문서가 섞인 코퍼스 |
| 원본 분석 | 35종 파싱, 기존 구조 오류 0 | 후보의 의미 정확도 전체를 확인한 것은 아님 |

| 레코드 | 일반값/120,000,000, 0, 긴 한글·특수문자/987,654,321 | 모든 업무 데이터 조합은 아님 |
| Fragment | 참가자격 절 교체 4쌍 | 시험 규칙으로 범위를 정하고 Grid 확정을 모의함 |
| 최종 합계 | **106건: 성공 49 / 차단 57 / 생성 후 검증 실패 0** | 차단은 생성 성공으로 세지 않음 |

성공한 단순 주입에서는 기대 문단 텍스트, 표·그림 수, 변경하지 않은 ZIP 항목 바이트 등을 검사했다. Fragment 삽입은 필요한 자원과 참조가 달라지므로 전체 ZIP 동일성을 요구할 수 없다. 변경 예정 항목과 불변 항목을 나누는 검사가 필요하다.

한 생성물은 RHWP 11쪽, 한컴 12쪽이었다. 합성 긴 문서도 RHWP 12쪽, 한컴 13쪽으로 달랐다. 페이지별 이미지/PDF 대조는 수행하지 않았다.

**49/106을 제품의 정확도나 일반 HWPX 호환율로 쓰면 안 된다.** 표본 선택과 필드 선택이 제한되어 있고, 아래 하네스 결함도 발견되었다. E6의 개별 성공 결과는 근거가 있지만 시험 프로세스가 exit 0이라는 사실만으로 전체 성공을 주장할 수 없다.

### 9.3 이번 문서 작성 중 재확인

`npm run verify`를 다시 실행했다. 샌드박스에서는 기존 시험 산출물 SVG/JSON을 덮어쓸 때 EPERM으로 중단되었다. 같은 검사를 호스트에서 재실행하자 구문·TypeScript·110파일 해시·읽기 전용 뷰어 경계와 **28개 시험이 모두 통과**했다. 제품 코드 수정은 없었다.

이번에는 기본 suite만 재실행했다. 106건 공고서 캠페인과 한컴 검사는 저장된 2026-10-02 보고서를 다시 읽었으며 재실행하지 않았다. 기본 suite 통과에도 아래 5개 결함은 미수정이다.

## 11. 차단 57건에 대한 해결 가설

### 11.1 혼합 서식 51건

한 값으로 잡힌 범위가 서로 다른 글자모양 run을 걸치면 현재 Core가 주입을 거부한다. 예를 들어 `120,000,000원(부가세 포함)` 전체를 Field로 잡았지만 실제 바꿀 대상은 숫자 부분뿐인 경우가 있다.

**제안:** 숫자 범위만 다시 잡고 `원`·괄호 설명·주변 글자 서식은 유지한다. 이때 포맷터가 `원`을 다시 붙여 `원원`이 되지 않도록 단위와 값 정책을 함께 바꿔야 한다.

이 세션의 앞선 해결방안 설명에서는 읽기 전용 조사 결과를 ‘차단된 17종의 33개 대상 중 금액 30개가 범위 축소 후보이고, 15종은 문제 대상 전부가 이 유형’으로 보고했다. 이에 따른 **15종 × 3행 = 45건은 개선 실험 후보**라는 추정이다. 이번 문서 작업에서 이 범위 조사를 다시 실행하거나 별도 저장 산출물로 재검증하지 않았으며, 이 방법으로 재생성해 45건이 성공한 결과도 아직 없다. 숫자 범위의 의미·출력 서식·데이터 정확성까지 확인해야 한다.

나머지 혼합 서식 문서는 사용자가 값을 넣을 범위와 적용 서식을 명시하거나 원본의 작업 사본에서 해당 Field만 정리하는 선택지를 검토한다. 첫 run의 서식으로 전체를 강제 통일하는 전역 우회는 원본 보존 요구와 충돌할 수 있다.

### 11.2 토큰 관련 6건

`{{구매/제조}}`, `{{#항목 현장설명회 현장설명회 안내}}` 같은 표현은 현재 토큰 문법과 맞지 않는다.

**제안:** 원문 토큰을 그대로 보관하고 Grid에서 안정적인 Field 또는 Block ID와 연결하는 별칭 매핑을 검토한다. 다만 두 번째 표현이 단일 값인지, 선택 블록인지, 반복 지시인지 이번 자료만으로 확정하지 않는다. 먼저 그 문법의 실제 의미와 원하는 출력 예를 확인해야 한다.

### 11.3 고칠 순서

검토 제안은 B1·B2와 B4를 먼저 고치고, B3·B5를 회귀 시험으로 고정한 다음 57건의 지원 범위를 확대하는 것이다. 안전한 차단을 없애는 것보다 잘못된 값이 성공으로 반환되는 경로를 먼저 막는다.

큰 플랫폼이나 새로운 언어를 먼저 추가하지 않고 기존 하네스에 증거를 쌓는 순서다. 인력·기간은 추정에 필요한 정보가 부족하므로 확정 일정이나 비용을 제시하지 않는다.

| P3 사용자 흐름 확인 | 가져오기→Grid→Block→레코드→적용→Preview→저장 재현 | 미확정 주입 금지, 수정 후 출력 무효화, 저장/복원 정확성 | 비전문가의 실제 수정·확정 작업 관찰 |
| P4 배치 품질 확인 | 대표 단문·장문·표 문서를 한컴에서 열고 비교 | 텍스트·표·그림·글꼴·줄/쪽 나눔에 대해 합의된 기준 충족 | 미관·제출 품질은 기계 구조 검사와 별도 판정 |
| P5 필요 기능 확대 | 의미 추천, 외부 DB, 배열 반복, 다중 구역 등 | 효과와 사용 빈도가 확인된 항목별 작은 PoC | 요구가 없으면 확장하지 않음 |

회귀 검사는 최소한 다음을 포함해야 한다.

- 데이터: 정상값, 0, 빈 값, 누락, 긴 한글, 특수문자, 식별자 앞자리 0, 템플릿처럼 보이는 문자열.
- 매핑: 같은 이름·다른 ID, 같은 값·다른 열, 명시적 병합, 점 포함 이름과 경로의 구분.
- 승인: Master와 donor 모두 미확정/확정 조합, 직접 작성 MD의 승인 정책.
- Block: 조건 임계값, 동률·기본값, 수동 선택 우선, 선택 저장·복원.
- HWPX: 누름틀 반복, Fragment 후 위치 변화, 스타일 경계, 표·자원 참조, Unwrap 후 텍스트 유지.
- 판정: 성공·예상 차단·뜻밖의 오류·미실행 분리, 원본 불변, 데이터 재파싱 대조, 한컴 대표 검증.

## 16. 아직 부족한 업무 정보

대표적인 문서 종류와 월 작성량, 현재 수작업 순서·소요시간, 반드시 보존할 표·글꼴·배치, 실제 데이터 출처와 문서-레코드 식별키, 누락값 처리, 반복 문단/표의 필요성, 추천이 틀렸을 때의 검토 부담은 아직 구체적으로 확정되지 않았다.

따라서 기술 검토에서는 이 정보를 임의로 채우지 말고, **어떤 판단에 어떤 정보가 필요한지** 표시해 달라. 다만 정보가 없어도 진행할 수 있는 B1~B5 수정 설계와 제한된 입력의 실험은 별도로 제안해 달라.

## 17. 설계자 답변 양식

다음 순서의 답변을 요청한다.

1. **판정:** 제한 없이 가능 / 범위를 제한하면 가능 / 현 접근의 수정 필요 / 근거 부족을 기능별로 구분.
2. **근거:** 확인한 소스·보고서 또는 필요한 실험. 실행하지 않은 판단은 가설로 표시.
3. **유지·수정·제외:** 기존 자산과 요구를 각각 어디에 둘지 이유와 함께 제시.
4. **권장 흐름:** 승인·데이터·Fragment·검증 경계를 포함한 최소 구조.
5. **우선순위:** 가장 먼저 막아야 할 오류와 그다음 지원 범위 확대를 구분.
6. **실험 계획:** 입력, 기대 출력, 실패 조건, 합격 기준, 대안 전환 기준.
7. **추가 질문:** 답변 없이는 결정할 수 없는 항목만 우선순위로 제시.
8. **작업 추정:** 범위를 확정한 뒤 산정하고, 조판·자료 품질·호환성 때문에 달라지는 부분을 별도 표시.

요청하는 것은 기존 설명에 대한 동의가 아니라, 사용자의 목적에 비추어 **어디까지 만들 수 있고, 무엇을 바꿔야 하며, 어떤 증거가 있어야 믿고 쓸 수 있는지**에 대한 기술적 판단이다.
