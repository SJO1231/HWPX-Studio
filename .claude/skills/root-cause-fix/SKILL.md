# 재현과 원인 근거로 버그 수정

증상 제거와 원인 해결을 구별한다. 실제 프로젝트의 기존 디버깅·테스트 절차를 따른다.

## 1. 재현과 독립 기대값

- 입력·환경·실행 순서·실제 결과·기대 결과를 확인한다.
- 기대값은 요구사항·외부 규격·독립 기준으로 정한다. 현재 잘못된 출력에서 역산하지 않는다.
- 가능하면 작은 재현 테스트를 만들고, 수정 전 대상 결함 때문에 실패하는지 확인한다.
- 준비 오류·누락 의존성 때문에 실패한 테스트는 결함의 재현 증거가 아니다.
- 자동 재현이 어려우면 단계·환경·산출물을 남긴다. 재현 불가를 해결 완료로 바꾸지 않는다.

## 2. 원인 범위 축소

- 오류 발생 지점에서 입력의 생산자·변환·소비 지점까지 필요한 경로를 추적한다.
- 정상 사례와 실패 사례를 비교한다. 차이를 설명하는 가설과 이를 판별할 최소 관측을 정한다.
- 한 번에 설명 가능한 변경을 한다. 무관한 수정 여러 개를 묶어 우연히 통과시키지 않는다.
- 같은 가설을 지지하는 새 근거 없이 수정이 누적되면 멈추고 가설을 재검토한다.
  횟수만 채우거나 성공할 때까지 재실행하지 않는다.

## 3. 수정과 회귀 확인

- 확정된 원인과 관련된 가장 작은 변경을 한다.
- 원래 실패 사례, 가까운 정상 대조군, 과잉 적용을 잡는 경계·반례를 검사한다.
- 테스트가 구현의 상수나 분기를 그대로 따라 쓰지 않는지 확인한다.
- 특정 파일명·사용자 ID·fixture 값만 예외 처리하는 우회는 일반 규칙의 근거가 있어야 한다.
- snapshot·golden·임계값 갱신으로 실패를 없애지 않는다. 기대 동작 변경이 목적이면 이를 별도로 설명한다.
- 프로젝트에서 요구하는 관련 검증을 실행한다. 추가 코드 변경 후 영향받는 검증을 갱신한다.

## 반환할 근거

- 증상과 재현 경로
- 확정 원인과 코드 위치; 미확정이면 그렇게 표시
- 변경 이유와 범위
- 수정 전 실패 → 수정 후 결과
- 정상 대조군·반례 결과
- 실행하지 못한 검사·남은 위험

수정 전에도 통과한 테스트는 이 버그의 재현 증거가 아니다.
중요한 입력·권한·계약이 불명확하면 해당 수정은 중단하고 필요한 질문을 한다.
