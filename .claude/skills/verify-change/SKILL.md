# 변경 주장과 실제 근거 대조

검사 명령이 성공했다는 사실과 사용자의 요구가 충족됐다는 사실을 연결한다.
리뷰 전용 요청이면 제품 코드를 고치지 않고 근거 있는 문제를 보고한다.

## 확인 순서

1. 요청, 성공 조건, 변경 diff, 실제 검증 대상의 버전·경로를 확인한다.
   검증 후 관련 파일이 바뀌었는지도 확인한다.
2. 중요한 주장별로 그 주장을 판정할 검사·관측·독립 기대값을 찾는다.
3. 기존 프로젝트가 정한 빠른 선검사와 필수 검사를 실행한다.
   변경과 무관한 대규모 검사 추가나 동일 검사 반복은 근거가 있을 때만 한다.
4. 종료 코드뿐 아니라 실제 실행 대상 수, 실패·경고·부분 실패 필드, 산출물 내용을 확인한다.
   대상 0건·검사 미발견·준비 실패를 통과로 세지 않는다.
5. 테스트·fixture·golden·기준선·coverage 제외 변경을 살펴 성공 기준 완화가 아닌지 확인한다.
6. 부분 성공과 전체 충족을 구별한다. 필요한 검증이 없으면 완료 범위를 축소해 보고한다.

## 대상별 추가 확인

해당하는 항목만 적용한다.

- 버그: 수정 전 재현, 수정 후 결과, 정상 대조군·반례가 실제 결함을 겨냥하는가.
- 리팩터링: 공개 동작·호출자·입출력 계약이 보존됐는가.
- UI·문서 렌더: 실제 화면이나 생성물을 열어 요청한 변화·깨짐·오버플로를 확인했는가.
  스크린샷을 보지 않았으면 시각 검증 완료라고 쓰지 않는다.
- 데이터 변환: 수량·식별자·중복·손실과 필요한 왕복 성질을 확인했는가.
- 배포 산출물: 검증한 파일과 전달·설치한 파일의 버전·해시 또는 빌드 정체성이 이어지는가.
  실행 환경의 차이를 파일 해시 일치만으로 입증하지 않는다.
- 문서·Skill: 원천과 내용, 참조 경로, 형식, 사용 조건을 확인했는가.
  형식 검사 통과가 모델의 실제 행동 품질을 증명하지 않는다.

## 보고

작은 변경은 짧은 문장으로 충분하다. 복수 주장에는 다음 열을 사용한다.

| 주장 | 대상·경로 | 기대 결과 | 실행·관측 근거 | 판정 | 남은 범위 |
| --- | --- | --- | --- | --- | --- |
| 확인할 주장 | 검사한 상태 | 독립 기준 | 명령·결과·산출물 | 충족 / 미충족 / 미검증 / 비해당 | 이유 |

- `충족`: 주장 범위에 해당하는 근거를 확인했다.
- `미충족`: 요구와 다른 결과를 관측했다.
- `미검증`: 실행·관측·기준이 부족하다.
- `비해당`: 적용하지 않는 근거가 있다. 편의상 생략한 검사는 여기에 넣지 않는다.

다른 Agent가 실제로 검토한 경우에만 독립 검토라고 쓴다.
위임이 허용되지 않거나 불필요하면 자신의 검토임을 밝힌다.
확인된 필수 검사 통과 후에는 새 변경·실패·미해결 우려가 없는 한 완료 보고로 진행한다.
