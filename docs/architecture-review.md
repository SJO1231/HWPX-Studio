## 1. 프로젝트 정의

HWPX Studio는 기존 `.hwpx` 문서를 바탕으로, 프로그래밍 지식 없이 템플릿을 만들고 JSON 또는 DB의 데이터를 문서의 특정 위치에 매핑해 **원 서식을 유지한** 새 HWPX 문서를 만드는 시각적 템플릿 저작 도구다.

| 계층 | 이름 | 책임 |
| --- | --- | --- |
| 제품 | HWPX Studio | 전체 |
| 문서 처리 | HWPX Engine | 패키지·XML·모델·조각·채움·쓰기·검사 (자체 구현) |
| 템플릿 편집 | Template Designer | 앵커·규칙(조건)·조각 배치 |
| 데이터 매핑 | Data Mapper | JSON/DB 트리, 매핑, 데이터 묶음 |
| 화면 | Viewer / Editor | 문서 표시·선택·편집창 (rhwp 사용) |
| 보조 | Jev-assist | 로컬 추천기(후보·매핑·앵커·서식·조건) |

사용자 지시(확정): rhwp는 뷰어와 편집창으로 쓴다. 엔진은 오픈소스의 원리만 참고해 자체 구현한다. HWPX를 파싱할 때 서식 정보까지 전부 추출해 JSON 또는 DB에 저장한다. 한 문서의 조각을 다른 문서에 보이는 그대로 삽입하는 것을 우선한다. 조건 분기는 내부적으로 JSON이고 사용자는 조건을 선택해서 만든다.

## 2. 핵심 Use Case

1. 기존 `.hwpx`를 연다. 엔진이 패키지와 XML을 서식까지 전부 파싱해 모델로 만든다.
2. 화면에서 문서를 본다(rhwp 렌더).
3. JSON 샘플·스키마 또는 DB를 불러온다. 트리로 본다.
4. Jev-assist가 채울 만한 자리를 후보로 보여 준다. 사용자가 고르거나, 필드를 문서 위치로 끌어다 놓거나, `{{`를 입력해 자동완성으로 연결한다.
5. 누름틀로 만들 수 있는 자리는 누름틀로 승격한다.
6. 조건 규칙을 선택형 화면에서 만든다: "이 데이터가 이 값이면 이 블록을 지운다 / 이 조각을 넣는다 / 이 표 행을 반복한다".
7. 다른 문서에서 가져온 조각(문단·표·그림)을 서식 그대로 삽입한다.
8. 시험 데이터를 적용해 미리 본다.
9. 템플릿 프로젝트를 저장한다.
10. 실제 데이터를 넣어 새 `.hwpx`를 만든다. 검증을 통과해야 저장된다.

1차 구현은 2·4의 화면을 뺀 나머지를 CLI로 수행한다.

| template | 앵커, 규칙(조건·액션), 데이터 묶음 | 1차(핵심), 2차(반복) |

| validate | 참조 무결성·중복·패키지·구조 검사, 저장 게이트 3방식 | 1차 |
| viewer | rhwp 렌더, 좌표↔앵커 변환, 편집창 | 2차 |
| mapper UI | JSON 트리, 드래그 매핑, 자동완성, 규칙 선택 화면 | 2~3차 |
| jev-assist | 후보·매핑·앵커·서식·조건 추천 | 2차부터 |
| 생성 모드 | md/txt에서 새 문서 생성 | 3차 |
| com | 한컴 COM 보조(문서 전체 삽입, PDF 대조) | 선택 |

## 4. 기술적 난점

| 난점 | 상태 | 근거 |
| --- | --- | --- |
| 문단 `id`가 고유하지 않다 | **[확인]** | 합성본에는 없고, 한컴 저장본은 91개 중 87개가 같은 자리값 |
| 한 문자열이 여러 run·`hp:t`로 쪼개진다 | **[확인]** | 시험 문서의 다중 run 문단 5~23개 |
| 텍스트를 바꾸면 조판 캐시(`linesegarray`)가 어긋난다 | **[문서]** | 어긋난 캐시로 한컴이 변조 경고를 내거나 글자가 겹친 사례가 참고 프로젝트 둘에 기록됨 |
| 원본 문서 자체에 오류가 있다 | **[확인]** | 실제 문서 659건 중 한컴류 15%에 id 중복·없는 참조 |
| 조각을 옮기면 서식 id가 다른 뜻이 된다 | **[확인]** | 자원 id는 문서마다 다르다. 복사가 아니라 재매핑이 필요 |
| 한컴 조판과 다른 엔진의 조판이 다르다 | **[확인]** | 쪽 수 비교 13건 중 12건 일치 |
| rhwp 저장은 전체 재직렬화다 | **[문서]** | 원본 소스 확인. 바이트 보존 경로가 없다 |
| rhwp에 문서 간 조각 가져오기가 없다 | **[확인]** | CLI·MCP·WASM 목록에 없음 |
| 누름틀 채움에서 값이 조용히 사라질 수 있다 | **[문서]** | 안내문과 같은 값을 넣으면 유실된 결함 사례 |
| 확장자만 hwpx인 파일 | **[확인]** | 659건 중 7건이 ZIP 아님 |
| 2024 네임스페이스 문서 | **[미검증]** | 표본 없음 |
| 그림·필드·중첩 표가 든 조각 이동 | **[미검증]** | 표·문단만 실측 |

## 5. HWPX 처리 구조

```
[데이터 계층]   dataset(원천 JSON/DB) + derived(파생: 포맷 값·계산 값·조각 바인딩)  — 템플릿과 독립
[문서 저장소]   model(서식까지 전부 파싱한 내부 모델: 자원 + 본문 + 미지원 요소 원문 + 오프셋)
[조각 라이브러리] fragment(블록 원문 + 자원 의존 닫힘 + 이진 자료 + 지문)
[템플릿]        template(앵커 + 규칙: 조건 → 액션)
        │
        ▼
[HWPX Engine]  parse → model
               extract / import fragment (지문 비교 → 재사용 또는 추가 → ID 재매핑)
               compile rules (데이터로 조건 판정) → edit plan (구간 치환 목록)
               apply (수정 구역만 구간 치환, header는 자원 추가만, 나머지 바이트 보존)
               validate (기준선 | 엄격 | 수리) → verify (재파싱·수량 대조·값 재읽기·오라클) → 저장 → 원장
        │
        ▼
[Viewer/Editor = rhwp]   [Jev-assist]   [Desktop shell]
```

### 5.1 문서 형식 (사용자 지시, 2026-10-01)

HWPX를 우선해 개발하되 Markdown과 일반 텍스트 문서도 다룰 수 있어야 한다. 그래서 계층을 둘로 나눈다.

| 계층 | 내용 | 형식 의존 |
| --- | --- | --- |
| 형식 중립 핵심 | 데이터 묶음, 값 해석, 조건 평가, 규칙(조건 → 액션), `{{}}` 문법, 적용 순서, 보고서, Jev-assist의 점수·학습 | 없음 |
| 문서 어댑터 | 열기, 자리(앵커) 찾기, 채움·삭제·삽입, 조각, 검사, 저장 | `hwpx`(1차 핵심), `md`·`txt`(1차 끝에 최소 구현) |

| 개념 | hwpx | md / txt |
| --- | --- | --- |
| 줄(`line`) | 문단 | 빈 줄로 나뉜 블록(md), 줄(txt) |
| 단어(`word`) | 문단 안 논리 텍스트 구간 | 줄 안 문자 구간 |
| 자리(`field`) | 누름틀 | `{{이름}}` 표기 |
| 오브젝트(`object`) | 표·그림·도형 | 표·코드 블록·제목 구획(md) |
| 셀(`cell`) | 표 셀 | 파이프 표의 셀(md) |
| 조각 | 블록 원문 + 서식 자원 | 텍스트 블록 |
| 검사 | 참조 무결성·패키지·구조 | UTF-8, 남은 자리, 표 열 수(md) |

- 같은 템플릿 규칙·데이터 묶음을 형식이 다른 문서에 재사용할 수 있다(앵커만 형식별로 다시 잡는다).
- 형식 변환(md → hwpx 새 문서 생성, hwpx → md 추출)은 별도 기능으로 뒤 단계에 둔다.

원 서식 유지는 네 단계로 지킨다.

1. **파싱**: 서식·자원·미지원 요소를 잃지 않는 모델(무손실 요소 트리 + 의미 색인).
2. **쓰기**: 수정하지 않은 바이트는 그대로 두고 변경분만 구간 치환한다. DOM 재직렬화를 하지 않는다.
3. **조각 이동**: 블록 원문과 그것이 의존하는 자원을 함께 옮기고, 대상 문서의 자원과 지문으로 비교해 재사용하거나 추가하고, id를 다시 매긴다.
4. **대조**: 결과를 원문과 서식 지문·렌더·한컴 열림으로 확인한다.

## 6. Viewer 구현 전략

| 방식 | 내용 | 난이도 | 정확도 | 판단 |
| --- | --- | --- | --- | --- |
| A | 자체 HTML 렌더러 | 매우 높음(조판 엔진) | 낮음~중간 | 기각 |
| B | 기존 라이브러리(rhwp WASM) | 낮음 | 중간~높음(한컴과 완전 동일은 아님) **[확인]** | **채택** |
| C | XML 기반 단순 미리보기 | 낮음 | 낮음(구조만) | CLI `inspect`와 폴백 |
| D | 한컴 COM 보조 | 중간(한컴 설치 필요) | 가장 높음 | 검증·PDF 대조 전용 |
| E | 한컴 조판 캐시 좌표로 그리기 | 중간 | 한컴 저장본은 높음, 수정 뒤는 근사 | 보류(원본 대조 보기 후보) |

결정(임시): 매핑 화면은 `@rhwp/core`(SVG 렌더, 좌표→문서 위치 변환, 글자별 좌표)를 쓴다. 템플릿 편집창은 rhwp 편집기를 임베드한다. 엔진(호스트)이 문서 상태·저장·구조를 소유하고, 편집창은 표시·선택·편집만 맡는다. 편집 진입 전에 round-trip 동일성 게이트를 통과한 문서만 편집을 허용하고, 통과하지 못하면 보기 전용으로 연다. 편집 결과는 엔진으로 다시 파싱해 모델에 반영하고 손실 여부를 수량 대조로 확인한다.

추가 검증 필요: 편집기 임베드는 HTTP(S) origin만 지원한다 **[문서]**. 데스크톱 셸에서 로컬 루프백 서버를 둘지 커스텀 스킴으로 될지는 2차 PoC에서 확인한다.

## 7. Anchor / Mapping 전략

### 7.1 앵커 5종

| 종류 | 가리키는 것 | 식별 |
| --- | --- | --- |
| `field` | 누름틀 | 이름 + 같은 이름 안 순번 |
| `word` | 문단 안의 단어·구 | 주소 + 논리 텍스트 오프셋 + 앞뒤 문맥 지문 |
| `line` | 문단(한 줄 단위) | 주소 + 문단 텍스트 지문 |
| `object` | 표·그림·도형 | 종류별 순번 + 객체 id + 지문 |
| `cell` | 표 셀 | 표 앵커 + 행·열 |

- 주소는 `[구역, 문단 서수, 하위목록 서수, 문단 서수, …]`이다. 문단 `id`는 쓰지 않는다.
- 누름틀로 할 수 있는 자리는 누름틀로 처리한다. `compile` 단계가 `{{}}` 표기와 사용자가 고른 후보 자리를 누름틀로 승격한다. 원본은 그대로 두고 승격본을 따로 저장한다.
- 템플릿이 한컴에서 다시 편집돼 서수가 어긋나면 지문·문맥으로 다시 찾는다. 유일하게 찾으면 "재배치"(경고), 여러 개면 "모호"(오류), 없으면 "없음"(오류)으로 보고한다.

### 7.2 규칙(조건 분기)

- 사용자는 화면에서 **조건을 선택**한다: `[데이터 경로] [연산자] [값]`을 고르고 and/or로 묶는다. 내부 저장은 JSON이다.
- 연산자: 존재, 비어 있음, 같음, 다름, 크기 비교, 포함, 목록 중 하나, 배열 길이, 정규식.
- 액션: `fill`(값 채움, 포맷), `delete`(문단·행·블록·객체 삭제), `inject`(조각 삽입 + 데이터 바인딩), `repeat`(표 행·블록 반복), `insertText`(일반 텍스트를 영역에 서식 지정해 삽입: 영역 서식 상속 또는 글자·문단 모양 지정).
- 조건은 데이터 기준으로 생성 시점에 판정한다. 적용 순서는 고정한다(삭제 → 삽입 → 반복 → 채움 → 텍스트 삽입, 문서 끝에서 앞으로).
- 같은 앵커에 충돌하는 액션(삭제와 채움 등)은 저장 전에 검사해 알린다.

### 7.3 데이터 묶음

- `dataset`(원천 JSON 또는 DB 조회 결과)과 `derived`(포맷한 값, 계산 값, 조각에 데이터를 묶은 결과)를 한 묶음으로 관리한다.
- 묶음은 데이터 경로와 조각 id로 식별한다. 템플릿의 위치에 묶이지 않으므로, 템플릿 일부를 고쳐도 계속 쓸 수 있고 다른 템플릿에도 쓸 수 있다.

### 7.4 프로젝트 저장 형태

폴더 구조로 시작한다(임시 선택). 한 파일로 묶는 형식은 2차에서 검토한다.

```
template-project/
  source.hwpx          원본(수정하지 않음)
  compiled.hwpx        누름틀 승격본(있을 때)
  project.json         이름·버전·원본 해시
  template.json        앵커·규칙
  model.json           파싱한 모델(다시 만들 수 있는 파생물)
  datasets/            데이터 묶음(원천·파생)
  fragments/           조각
  schema.json          데이터 스키마(선택)
```

## 8. Electron vs Tauri

| 기준 | Electron 44 | Tauri 2 |
| --- | --- | --- |
| XML/ZIP 처리 | 엔진(TS)을 Node 프로세스에서 그대로 실행 | WebView에서 실행하거나 Rust로 다시 작성 |
| 파일시스템 | Node `fs` | 플러그인·권한 선언 |
| 로컬 파일 드래그 | `webUtils.getPathForFile` | 경로 이벤트와 HTML5 DnD가 상충(Windows) **[문서]** |
| Windows 지원 | Chromium 번들 | 시스템 WebView2 |
| 개발 난이도 | 낮음(TS 한 언어) | Rust 도구 필요 |
| 디버깅 | DevTools 내장 | WebView2 DevTools + Rust |
| 패키징 | 성숙. 바이너리는 ASAR 밖에 둬야 함 | NSIS/MSI, sidecar 선언 |
| 최종 용량 | 150MB 이상 | 수 MB + WebView2 |
| COM/한컴 연동 | Node에서 자식 프로세스 | sidecar로 가능 |

결정(임시): **Electron**. 엔진이 TypeScript이고 사이드카(검증 오라클, COM 보조)를 쓰기 쉽고 디버깅이 편하다. UI는 웹 기술로만 만들어 Tauri로 옮길 여지를 남긴다. 용량이 결정 요인이 되면 2차 뒤에 다시 평가한다.

## 16. Jev-assist 설계

로컬·오프라인·저사양에서 도는 추천기다. 모든 결과는 **제안**이며 점수(0~100)와 근거를 함께 보여 준다. 자동 적용은 기본으로 끈다. 사용자가 확정한 것만 학습한다. 파생 데이터는 지워도 사용자 자료가 남는다.

| 단계 | 방법 | 자원 |
| --- | --- | --- |
| 0 | 규칙 + 글자 n-gram 유사도 + 최근접 이웃 | 모델 없음, 메모리 0.1~0.2GB |
| 1 | 소형 임베딩(선택) | 약 140MB 다운로드, 0.5~0.75GB |
| 2 | 소형 로컬 LLM(선택, 사용자가 부를 때만) | 약 1GB + 실행기 |

활용처:

| # | 활용 | 입력 → 출력 | 단계 |
| --- | --- | --- | --- |
| 1 | 채움 후보 자리 탐지 | 문서 모델 → 누름틀 후보(라벨 옆 빈 셀, 헤더행 표, `라벨: 값`, 괄호·밑줄 빈칸, 체크박스, `{{}}`) | 0 |
| 2 | 데이터 키 매칭·일치 검증 | 후보 자리 × JSON 리프 → 점수(라벨↔키 유사도, 한/영 동의어, 값 형식↔자리 타입) | 0 |
| 3 | 앵커 보조 | 수정된 템플릿 × 기존 앵커 → 재배치 후보 순위 | 0 |
| 4 | 서식 패턴 추정 | 삽입 영역 주변 문단·라벨·확정 이력 → 적용할 글자·문단 모양 제안 | 0~1 |
| 5 | 조건 규칙 추천 | 데이터의 값 분포(불리언·열거·빈값) × 블록 문맥("해당 시", 체크박스) → 규칙 후보 | 0 |
| 6 | 조각 추천·중복 탐지 | 삽입 위치 문맥 × 조각 라이브러리 → 유사 조각, 같은 조각 묶기 | 0~1 |
| 7 | 데이터 품질 점검 | 데이터 묶음 × 템플릿 요구 키 → 누락·형식 이상·중복 보고 | 0 |
| 8 | 값 포맷 추천 | 자리의 기존 값 패턴 → 날짜·숫자·전화 포맷 | 0 |
| 9 | 표 행 반복 후보 | 배열 데이터 × 헤더행 표 → 반복 규칙 후보 | 0 |
| 10 | 템플릿 전이 | 새 문서 × 확정된 템플릿들 → 유사 템플릿의 매핑 제안 | 0~1 |
| 11 | 결과 이상 요약 | 생성 전후 수량·쪽 수·남은 자리 → 우선순위 목록 | 0 |
| 12 | 자동완성 순위 | `{{` 입력 위치 문맥 → 키 순위 | 0 |
| 13 | 자연어 요청(선택) | "채울 곳 찾아줘" 같은 요청 → 위 기능 호출 | 2 |
| 14 | **자동 템플릿 초안** | 문서 1개 또는 같은 서식의 문서 여러 개 → 템플릿 초안(누름틀·`{{}}`·JSON)과 데이터 초안 | 0 |

판정 규칙: 임계값 기본 80, 같은 라벨이 여러 곳에 걸리면 자동 확정하지 않는다, 학습 자료는 사용자 확정 매핑뿐이다.

### 16.1 자동 템플릿 제작 (사용자 지시, 2026-10-01)

문서를 넣으면 패턴을 분석해 템플릿 초안을 만들고, 사용자가 확인해 확정한다. 자동으로 확정하지 않는다.

**문서 하나일 때 (패턴 분석)**

1. 후보 자리 탐지(활용 1)로 누름틀 후보를 모은다.
2. 값처럼 보이는 구간을 찾는다: 날짜·금액·전화·주민번호 형식, 라벨 옆 셀의 내용, 괄호·밑줄 빈칸.
3. 자리 이름을 인접 라벨에서 짓고(예: "성명" → `성명`), 타입을 값 패턴에서 추정한다.
4. 초안: 앵커 목록 + 데이터 스키마 + 이 문서에서 뽑은 값(첫 데이터 사례).

**같은 서식의 문서 여러 개일 때 (대조)**

1. **정렬**: 문서들의 문단·셀을 주소와 텍스트 유사도로 짝짓는다(표는 행·열, 본문은 문단 순서 + 글자 n-gram).
2. **고정/가변 구분**: 짝지은 문단의 글을 비교해 모든 문서에서 같은 부분은 고정 글(뼈대), 달라지는 구간은 가변 자리로 본다.
3. **구조 차이**: 일부 문서에만 있는 블록은 조건 블록 후보, 행 수가 다른 표는 반복 후보로 표시한다.
4. **이름·타입**: 가변 자리의 이름은 인접 라벨이나 앞뒤 고정 글에서 짓고, 타입은 값들의 공통 패턴에서 정한다.
5. **초안**: 템플릿(앵커 + 규칙 후보) + 데이터 스키마 + 문서별 데이터 사례(각 문서에서 뽑은 값). 이 데이터 사례로 템플릿을 다시 채워 원래 문서와 같아지는지 확인한다(자기 검증).
6. **확정**: 사용자가 자리마다 승인·이름 변경·제외를 고른다. 승인한 자리는 누름틀로 승격하거나 `{{}}`·JSON 앵커로 저장한다.

- 출력 형태는 셋 중에서 고른다: 누름틀이 든 HWPX, `{{이름}}` 표기가 든 HWPX, 원본을 건드리지 않는 JSON 템플릿.
- 계산은 문자열 정렬과 비교라서 모델이 필요 없다. 문서 수가 많으면 표본만 쓴다.
- 한계: 서식만 다르고 글이 같은 차이는 가변 자리로 잡지 않는다. 문단 순서가 크게 다른 문서들은 같은 서식으로 보지 않고 대조를 거절한다.
- 단계: 2차(문서 하나)와 3차(여러 문서 대조). 엔진의 주소·논리 텍스트 모델 위에서 구현한다.

## 17. 라이선스 규칙

- 참고 프로젝트는 원리만 참고한다. 코드, 함수·변수·상수 이름, 주석, 파일 구조를 가져오지 않는다. 명세를 먼저 쓰고 명세에서 구현한다.
- 런타임 의존은 rhwp(MIT)와 Node 내장뿐이다. 고지 파일은 rhwp 1건이다.
- AGPL·LGPL·라이선스 미표기 저장소는 참고 대상에서도 뺀다.
- 검증 오라클은 개발용이며 배포물에 넣지 않는다.
- 완료 검증에 식별자 대조 점검을 넣는다.

## 18. 추가로 권하는 사항

1. **규칙 시험 표**: 데이터 사례 여러 건과 기대 결과를 묶어 템플릿 회귀 시험으로 쓴다. 규칙을 고칠 때마다 전 사례를 모의 실행한다.
2. **채운 값 재읽기 대조를 필수 게이트로** 둔다. 성공 보고와 실제 산출물이 어긋나는 일을 구조적으로 막는다.
3. **원장**: 입력 해시, 템플릿·데이터 묶음·조각 버전, 검증 결과를 남겨 같은 결과를 다시 만들 수 있게 한다. 값 원문은 남기지 않는다.
4. **일괄 생성**: 데이터 여러 행으로 문서 여러 개를 만드는 경로를 CLI부터 둔다.
5. **스키마 버전**: `template.json`, 조각, 데이터 묶음에 버전과 옮기기 규칙을 둔다.
6. **템플릿 drift 검사 명령**: 원본이 바뀌었을 때 앵커 상태를 한 번에 보고한다.
7. **한컴 실기 검증의 정례화**: 한컴이 설치된 PC에서 열기·쪽 수·PDF 대조를 슬라이스마다 돌린다.
8. **입력 방어**: 암호·DRM·압축 폭탄·형식 위장을 열기 단계에서 거른다.
9. **폰트 안내**: 화면 조판은 설치된 폰트에 좌우된다. 대체 폰트를 쓴 경우 화면에 표시한다.
10. **규칙 충돌 검사와 미리보기**: 규칙을 저장하기 전에 같은 앵커에 걸린 상충 액션을 알리고, 조건별 모의 실행 결과(지워질 블록, 들어갈 조각)를 화면에서 보여 준다.
