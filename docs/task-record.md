## 판단

### 사용자 결정

- rhwp는 뷰어와 편집창으로 쓴다. 엔진은 자체 구현한다.
- 오픈소스는 원리만 참고한다. 코드·식별자를 가져오지 않는다. 라이선스 고지가 필요한 의존은 복잡한 것에만 쓴다.
- HWPX를 파싱할 때 서식 정보까지 전부 추출해 JSON 또는 DB에 저장한다. 한 문서의 조각을 다른 문서에 보이는 그대로 넣는 것을 우선한다.
- 앵커는 줄·오브젝트·단어 단위를 지원한다. 누름틀로 가능한 자리는 누름틀로 한다.
- 2차 순서(2026-10-02): 편집창은 미루고 뷰어 위에 매핑·조건 선택·표 조정 화면을 먼저 만든다. (그동안 내용 수정을 한컴에서 하는 것은 총괄의 임시 선택이며 사용자가 따로 정한 것이 아니다.)
- 데이터(2026-10-02): JSON으로 받아 DB에 넣어 둔 데이터를 쓴다. 값에 줄바꿈이 제법 있다. 어떻게 넘길지는 미정(사용자가 방법을 모른다고 함).
- 참고 후보 적용(2026-10-02): 참조 번호 자동 재정렬, 상호 배타 규칙을 조건 분기 템플릿에 넣는다.
- 다음 순서(2026-10-04): 여러 문단에 걸친 누름틀과 줄바꿈·탭이 든 누름틀을 한컴 방식(첫 문단에 값, 사이 문단 삭제, 끝 뒤 글 합침)으로 채우는 엔진 보강을 먼저 한다. 사용자가 "채울 수 없는 모양이면 밀어넣을 수 없나"라고 묻고 "1부터 먼저 시행"이라고 했다. 그 뒤 화면 순서는 여전히 결정 대기.
- 조건 분기: 조건에 따른 삭제와 사전 파싱 데이터 주입을 둘 다 지원한다. 내부는 JSON이고 사용자는 조건을 선택해서 만든다.
- 파싱 데이터와 파생 데이터를 묶음으로 관리하고 다른 템플릿에도 재사용한다. 서식을 지정한 일반 텍스트 삽입을 지원한다.
- Jev형 로컬 도우미를 후보 추천, 데이터 일치 검증, 앵커 보조, 서식 패턴 추정, 조건 추천, 자동 템플릿 제작에 쓴다. 결과는 사용자가 확정한다.
- HWPX를 우선해 개발하되 md·txt 문서도 다룰 수 있어야 한다.
- 문서를 넣으면 패턴을 분석해 템플릿 초안을 자동으로 만들고, 필요하면 여러 문서를 대조한다. 사용자가 확인해 확정한다.
- 저장 게이트는 기준선·엄격·수리 세 방식을 모두 둔다.
- 시험은 합성 문서로 끝내지 않는다. 서로 무관한 실제 문서 사이에서, 길고 복잡한 구간을, 통째와 쪼갠 방식으로 삽입해 본다. 서식 변경과 드문 서식도 적용해 본다. 오류 검출과 보정을 병행한다.
- 시험 자료: 합성 문서와 한컴 저장본, 그리고 실제 문서 모음을 읽기 전용으로 쓴다.
- Git: 로컬 커밋을 먼저 하고 정제된 내용만 원격에 올린다. 개인적인 내용과 불필요한 내용은 뺀다.

### 확인 사실

- 문단 `id`는 고유하지 않다(한컴 저장본 91개 중 87개가 같은 값).
- 실제 문서 659건 중 81%가 검사기를 통과했고, 한컴류 15%에는 원래 id 중복·없는 참조가 있다.
- 표·문단 조각을 다른 문서로 옮기는 실험에서 서식 지문이 전부 같았고 한컴에서 열렸다. 그림·필드·중첩 표는 시험하지 않았다.
- rhwp의 HWPX 저장은 전체 재직렬화이고 문서 간 조각 가져오기가 없다.
- 한컴과 rhwp의 쪽 수는 13건 중 12건이 같았다.

### 임시 선택 중 중요한 것

- 쓰기는 구간 치환과 ZIP 레코드 복사로 한다. DOM 재직렬화를 하지 않는다.
- 텍스트가 바뀐 구역은 줄 배치 캐시를 전부 지운다.
- 누락 키의 기본 정책은 오류다.
- 데스크톱 셸은 Electron이다.
- 스타일 이름이 충돌하면 대상 문서의 것을 우선하고 새 스타일에 접미사를 붙인다.

## 다음 담당자에게

- 첫 행동: `npm install` → `npm run typecheck` → `npm test`로 현재 상태를 재현한다. 오라클을 켜려면 `HWPX_ORACLES=1`(rhwp 실행 파일과 Python이 있을 때).
- 다음: 엔진 보강(여러 문단·인라인 누름틀을 한컴 방식으로 채움)은 구현·독립 검증·재검증까지 끝났다([검증 기준](validation.md) 16절). 남은 과제는 GitHub 이슈로 등록해 처리한다(초안: 누름틀 종류 판정 보완, 결과 크기 가늠, 셀·문단 채움의 잔존 요소, 생성물 개인정보 정리, 중첩 누름틀 버림 표시, 첫 화면 검토, 단계 종료 검토). 화면 순서(S1 매핑, S3 조건, S7 조각·표)는 사용자 결정 대기. 편집창을 미룰지 먼저 할지도 사용자 답을 기다린다([진행 방향](roadmap.md)).
- 뷰어에서 배운 것: 구현 쪽 전수 대조가 "0건"이어도 재는 경로가 실제 사용 경로와 다르면 결함을 놓친다. 독립 검증은 사용자가 실제로 누르는 경로로 잰다.
- 알려진 한계: 표 조정의 한계는 [엔진 명세](engine-spec.md) 7.91. 셀보다 넓은 내용의 가로 잘림은 경고하지 않는다. 한컴은 13 한 버전으로만 확인했다. 양식 개체의 테두리 종류 참조, 차트 참조 등은 번역하지 않고 경고한다. 템플릿의 원본 해시(`source.sha256`)는 아직 대조하지 않는다. 줄 앵커는 해시가 필요해 손으로 쓰기 어렵다(화면에서 만들 것을 전제).
- 사용자 결정 대기: 화면과 편집창의 순서, 데이터를 넘기는 방법(견본 한 건 또는 DB 종류), 연결한 자리를 누름틀로 바꾼 사본을 원본으로 쓸지, 혼자 쓰는지 여럿이 쓰는지([스튜디오 명세](studio-spec.md) 6절). 알려 둔 것: 다른 프로젝트의 클래스 이름과 겹치는 설명적 타입 이름 6개를 그대로 둘지([참고 프로젝트](reference-projects.md) 0절). 더해진 대기 항목(2026-10-03): 다음 화면 순서(S1 매핑·S3 조건·S7 조각·표), 여러 문단 누름틀 채움을 앞당길지, 사용자가 만든 `HWP-Studio-lite` 가지를 지울지.
- 실제 문서 모음은 읽기 전용으로만 쓰고 이름·내용을 기록하지 않는다. 한컴 저장본을 시험 자료로 넣을 때는 `tools/fixtures/scrub-metadata.ts`로 작성자 정보를 치환한다.
